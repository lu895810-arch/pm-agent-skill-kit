# 结构手册（cyx-summary-need）

逐段写什么、必填什么、常见错误。顺序对应 SKILL.md 第 1 章骨架。

---

## 0. 审阅层

**评审速览表**（维度 / 结论，约 8–10 行）：核心定位 · 模式/范围 · 核心价值 · 功能模块数 · P0 范围 · 商业模式 · 运行环境 · 待确认数 · 风险 Top3。

- 评审核对的是「要不要做、范围对不对」，不是细节。结论写判断，不写过程。
- 常见错误：把功能清单抄进速览（速览只放维度级结论）；风险只列不排 Top3。

**头部三件**（顺序固定）：`.hero-t` 主标题 + 青色副标题 → `.kick` **产品核心摘要（≤60 字，见下方）** → 徽章与 KPI 卡。

**文档信息表**（项 / 内容）：文档名 / 版本 / 编制日期 / 内容基线（来源） / 状态 / 关联文档。**「版本」一格只写版本号 + 「版本沿革见附录 C」**，流水不在这里展开。

---

## 1. 产品概述

- **定位与核心价值**：一句话定位 + 3–4 条核心价值（每条「标题 + 一句说明」）。别说「一条流程完成低门槛创作」，说清它**解决了谁、在什么情境下的什么麻烦**。
- **解决的问题**：`痛点 / 现状描述 / 本产品回答` 三列表，最后一列是判断不是复述。
- **目标用户**：`画像 / 典型特征 / 核心诉求` 三列表，画像要落地到具体人群，不写「广大用户」。
- **运行环境与语言**：入口、终端适配、语言。未定义的范围显式标「待确认」。
- **产品演进背景 / 入口架构 / 核心需求主线（可选）**：素材里有演进、现状或竞品材料时才写。演进背景用「阶段 / 产品形态·核心入口 / 解决的核心痛点 / 目标用户 / 遗留问题」五列表——**最后一列写「这一步没解决、催生了下一步的」，它是整张表的信息量所在**。入口架构用 `ul.pts` 按**使用目的**排序（「① 快速测试 ② 快速粗片 ③ 出海分发 ④ 自主创作 / 团队生产 ⑤ 精细制作」），不按产品内部命名排序。需求主线归纳到 3 条以内，每条一句判据。三块都要在 `.dim` 或 `.note` 里说明「据演进分析归纳」，与材料事实区分开：归纳结论不能当产品事实用。
- **收口用 `blockquote`**：把最扎眼的那个遗留问题单独点出来（`<span class="lbl">最大遗留 UX 问题</span>` + 一句话），别埋在一堆列表里。

---

## 2. 名词术语表

- `术语 / 定义` 两列。凡第 3 章出现的自造概念必须在此有定义。
- 定义给「是什么 + 为什么叫这个名」的白话，不拿同义词当解释。
- 阶段性边界（「创建后不可改」「商业化后启用」）写进定义，并标清时点。

---

## 3. 功能需求（主体）

每个模块一节（`3.1 输入与结构化（P0）` 这种标题）。表头：`编号 / 功能点 / 说明 / 优先级 / 验收要点`。

- P0 必须有可测验收要点（「X 操作后 Y 可见」），不写「体验良好」这类不可测描述。
- 说明里避免「支持 / 优化 / 提升」空话，写清系统做什么、边界在哪。
- 约束性事实（如「创建后不可修改」「上限 10 万字」）用 `.note` 行强调，不要埋进长句。
- **模块引言（表前 `p.dim`）**：一句话交代这个模块是什么、分几层、哪些入口共用。例：协作模块表前写「协作分两层：协作编辑（项目级）……资产库分享……；该能力属于项目操作台本身，三种入口进入的项目都能用」——不写这层，读者看到表里的「协作邀请」与「资产库分享」会当成两件事。
- **模块说明注（表后 `.note`）**：每张表后跟一条，写**机制成因 / 实操口径 / 避坑**，不复述表格。三种常见写法：① 机制成因（「解析按集计费，是因为多层模型调用产生相对固定的处理成本，不按字读取」）；② 实操建议（「资产较多时先批量生成角色、确认形象后再做场景道具，避免批量返工」）；③ 约束强调（「上限 10 万字」「重新解析会创建新项目，不覆盖已有项目」）。
- **模块标题括号里放模块字母**（`3.1 输入与结构化模块（A）`），不放优先级——一个模块里往往同时有 P0 与 P1 行，标题挂 `（P0）` 会和表内自相矛盾。

---

## 4. 业务流程

- 用 `<pre>` 写 ASCII 流程图，箭头用 `↓`，阶段用空行分隔。
- 每条流程配一行 `.note` 规则注（重试次数、必校验项、覆盖关系）。
- 多模式各给一张图，标明差异点；条数按入口数来：主流程 / 各替代模式 / 独立业务模式（如转绘）/ 独立单点工具（如单镜头工作台）/ 精细制作层（如节点画布）。
- **最后可加一条「用户旅程视角的需求流转」**：把各入口按用户成长路径串成一条递进链（体验 → 粗产 → 出海 → 工程化 → 精修），`.note` 里点明「每一步的卡点催生下一步能力」。这条不引入新事实，只把前面几条流程的先后关系讲清楚。

---

## 5. 定价与计费（可选但产品常需）

- `计费项 / 口径 / 来源` 三列表。口径写清单位（元 / 积分 / 秒）与适用条件。
- 单位不统一（如「元/集」与「积分/秒」混用）必须进待确认 B 项，不硬凑。

---

## 6. 非功能需求

- `类别 / 要求` 两列：数据安全 / 稳定性 / 性能 / 提示约束 / 可扩展。
- 要求落到机制（「跨账号数据隔离」「历史版本持久化」），不写「安全可靠」这类形容词。

---

## 7. 约束与风险

- `编号 / 约束·风险 / 等级 / 对策` 四列。等级用 `高/中/低`，对策要落到具体机制。
- 常见错误：对策写「加强关注」（不可执行）；等级全标「中」（无区分度）。

---

## 8. 验收冒烟清单

- `ul.pts` 列端到端场景（不写单元测试）：主链路跑通 + 异常场景若干（制造一次失败、一次冲突、一次拦截）。
- 每条以「……——全程无阻断 / 可见 / 归集正确」收口。

---

## 9. 后续迭代需求池（可选）

- 素材里有演进 / 现状分析、并归纳出了「现在没做、以后可能做」的缺口时才写；位置在验收清单之后、附录之前。
- 开头给一段 `p.dim` 划范围：**这些缺口不在本文档当前主需求范围（模块 A–H）内**，是否纳入、优先级如何需产品确认。
- 表头 `编号 / 缺口 / 说明 / 建议优先级`；编号用 `G-1` 这种带连字符的写法，与第 3 章的模块编号 `G1` 区分开。
- 「建议优先级」列的值是**推断**，写 `P2（待确认）`，并在表头或引言里说明「本列为演进分析推断，非定论」。
- 常见错误：把缺口和主需求混在一张表里（读者分不清哪条要现在做）；缺口说明只写「优化 X」，不写清缺什么、导致什么后果。

---

## 附录 A 待确认清单

- `编号 / 问题 / 建议责任方 / 状态`。状态三档：`待确认` / `部分确认` / `已确认`。
- 从正文抓取所有「待确认」字样汇总，一条不落；编号连续。

## 附录 B 参考来源

- `来源 / 用途` 两列。用途写清这份来源支撑了文档哪部分，不写「参考资料」这类空话。
- **按来源级别分组**：原始材料（白皮书、业务介绍、官网、教程 / 知识库、模板）在前；「演进分析 / 现状梳理 / 缺口清单」类归纳文档单独一行在后，用途写明「仅支撑演进背景与后续迭代需求池」。
- 用途写到「喂了哪几节」的粒度，例：「主流程、资产与分镜能力、生图与视频模型、解析按集计费、比例与风格、成本优化技巧」。
- 页脚补一句口径声明：**不引用同空间其他衍生 PRD 作为事实来源**。

## 附录 C 文档口径与变更记录

- 位置在附录 B 之后；nav 加「口径」链接，锚点 `id="appC"`。**不是可选项**：口径与边界必写。
- **两块都用 `ul.pts` 分条分点，不许写成一整段**：

| 块 | 写什么 | 条数 |
|---|---|---|
| 口径与边界 | 内容基线（含哪些归纳型文档只作演进来源）/ 口径冲突怎么处理 / 推断怎么标 / 文档定位与交付标准 | 4–5 条 |
| 变更记录 | 倒序（最新在上），一个版本一条 `<li>` | 第二版起累积，首版写「首版」 |

- `文档定位` 一条要写清交付标准（「能看、能讲、能填数据」）与**不做什么**（不写 EARS 工程粒度，需要时另出重型 PRD）——读者据此判断该拿这份文档干什么。
- 有界面观察类来源的，`口径与边界` 再加一条「界面观察」：怎么与材料口径区分、冲突时两条都留。
- 单个版本改动多时嵌一层 `<ul>` 分子项，**按模块或按「续补 / 校正 / 调整」分组**，不要一长条糊在一起。
- **只记对外可见的变化**：口径、结构、条目增删、行序。不记排版微调、错别字、内部返工。
- 常见错误：① 变更流水同时写在头部 `.kick` 与「文档信息 · 版本」两处——必然不同步，且把摘要挤没了；② 口径说明写成一句超长句（应分条）；③ 版本条目只写「若干优化」（写了等于没写）。

### 头部 `.kick` 怎么写

一句产品核心摘要，**≤60 字**，讲清「面向谁 + 输入什么 + 经什么链路 + 自动产出什么」：

> 面向 {{目标人群}} 的 {{产品形态}}：{{输入什么}}，在 {{核心链路}} 一条工作流里自动生成、逐项可改，最终 {{产出物}}。

**不写**来源清单、口径归属、变更流水、文档定位——全是附录 C 的活。判据：**把这句话念给一个没听过这产品的人，他能不能说出这产品是干什么的？** 说不出来说明写成了元信息。

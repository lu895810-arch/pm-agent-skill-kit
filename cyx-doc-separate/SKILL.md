# cyx-doc-separate — 文档分区与精简归档

## Purpose（目的）

把「素材」和「成品」在**呈现上分区、在磁盘上分目录、在版本上分层**，并且**控制文件总量**——一件事只约定一次，之后每一轮都不用重复交代规则。

要解决的五个真实毛病：

1. 附件原文被大段搬进成品正文，读者分不清哪句是结论、哪句是抄来的资料；
2. 每轮迭代都新存一个版本文件，草稿和备选方案堆满文件夹；
3. 同一份参考文档被反复存档，说不清哪个是原件；
4. 改错了想回退，却发现旧版已被覆盖；
5. 一堆文件名看不出先后——有的带 `1-`、有的带 `-前`、有的是裸名，**光看文件名不知道哪个更新**。

一句话：**素材只存一份、成品只出一版、草稿默认不留、旧版只归档不删除、文件名自带更新序号。**

## When to use（何时触发）

**触发条件很宽**——只要本轮存在「文档形态的产出物」，就套用本 skill：

- 写方案 / 报告 / 总结 / 纪要 / 说明 / 测评 / 提案 / 周报 / 复盘
- 生成或改写 Word、PPT、Excel、Markdown、HTML、PDF
- 加工用户给的材料：整理、汇总、改写、提炼、翻译、结构化
- 多轮迭代：在上一版基础上补素材、改口径、升版本

**不触发的情形**（避免把日常对话也套上模板，反而啰嗦）：

- 纯问答、知识解释、闲聊、代码调试等**没有文档成品**的对话
- 用户明确说「不用分区格式，直接给我正文」
- 单次性的短输出（一句话结论、三行清单），套模板的收益低于成本

判断口径：**本轮结束时用户会拿到一份可以「存档 / 转发 / 再迭代」的东西吗？** 会，就触发。

## 两个区（核心定义）

### 【附件备份区】

存：用户上传/粘贴的原始文档、参考资料、背景素材、已定稿的历史交付版本。

权限：**只读**。只做三件事——存储、建索引、被检索引用。

- 索引字段：`文件名｜简要说明｜标记【原始素材 / 历史归档交付物】`
- **同一份原始素材只保留 1 份备份，禁止重复存档**（判重按内容指纹，不按文件名）
- ❌ 不存临时草稿、试写片段、备选方案——临时内容默认不归档，仅用户明确要求才保留
- 不在对话内粘贴完整原文，避免上下文膨胀
- 引用时只写编号：`参考附件2`

### 【本次产出区】

存：本轮任务的**唯一一份正式交付文档**。

权限：**独占写入**。这里出现的每一句都应该是本次创作的（结论、判断、结构、写法），不混入原始附件原文。

- 默认**只输出最终定稿版本**，不主动输出多版中间草稿、备选文本
- 迭代时**直接更新当前交付物**，版本号 +1，而不是另存新文件
- 引用参考资料仅标注 `参考附件N`，禁止大段复制原文嵌入交付正文

## 强制输出格式

每次交付，严格按此顺序输出，分割线原样保留：

```
【附件备份区 - 索引清单】
附件1：文件名｜简要说明；标记：原始素材 / 历史归档交付物
附件2：文件名｜简要说明；标记：原始素材 / 历史归档交付物
更01：历史产出 v1.0（已归档）｜上一版成品，仅备查；标记：历史归档交付物
---=== 分割线 ===---
【本次产出区：交付物名称｜更N · 版本】
（此处为本次定稿成品正文）
```

细则：

- **索引永远排在成品前面**，即使本轮只是小改一行也要列；
- 每条索引必须齐三要素：**编号 + 名称 + 简要说明**，再加**标记**；
- 附件编号 `附件N` 与交付物序号 `更N` 是两套编号，各自独立：附件按入库顺序，更N 按交付迭代顺序；
- 编号一旦分配就不复用、不重排，新增的往后顺延；
- 历史版本产出也进索引，用它的原始 `更N` 标注并写明 `历史产出 vX.Y（已归档）`；
- 版本号用 `v主.次`：**小改用次版本（v1.1），结构性重写用主版本（v2.0）**；
- **产出区标题同时给出更N与版本号**，读的人一眼知道这是第几次迭代、属于大改还是小改。

## 文件命名规范（「更N」前缀）

**交付物文件名一律以「更N」开头**，形如：

```
更01-AI教育厂商调研总结报告-20260914.md
更02-AI教育厂商调研总结报告-20260916.md
更03-AI教育厂商调研总结报告-20260920.md
```

| 组成 | 说明 |
| --- | --- |
| `更` + 两位数字 | 更新序号，即这一份是第几更。**放最前**，文件管理器按名称排序时直接看出先后 |
| 交付物名称 | 同一个交付物的历次更，名称必须完全一致，靠它把一条更新链串起来 |
| `YYYYMMDD` | 产出日期，紧凑写法 |
| 扩展名 | `.md` / `.docx` / `.html` … |

三条规则：

- **序号零填充两位**：写成 `更01`、`更10`，不能写 `更1`、`更2`。否则纯字符串排序会把「更10」排到「更2」前面，前缀就失去意义了。
- **归档时序号原样保留**：`更02` 进了 `_archive/` 之后还是 `更02`，不会重编号。所以把 `deliverables/` 和 `_archive/` 混在一起看，仍是一条读得出来的更新链（更01 → 更02 → 更03）。
- **不再用临时性后缀**：`-前` / `-旧` / `-副本` / `-final` / `-v2` 这类手工标记一律由「更N」取代。同一个名字的多次修改，靠更N 表达顺序，靠 `_archive/` 表达归档。

> 为什么要放最前而不是放最后：放最后（如 `名称-更01`）时，文件管理器按名称排序会把**不同交付物**的更号混在一起排；放最前才能形成「先按交付物聚簇、簇内按更号递增」的自然顺序。

## 归档与文件管控（解决文件夹混乱的核心）

### 三级目录规范

所有产出自动归入对应目录，**不允许文件散落在根目录**：

```
reference/          原始参考素材（仅存原件，不修改）
deliverables/       正式交付文件，命名 更NN-名称-YYYYMMDD.ext
    _archive/       历史版本归档（序号原样保留，不删除）
tmp_drafts/         临时草稿，定期批量清理，不长期留存
archive_index.md    总归档清单，与对话内【附件备份区索引】保持同步
```

需要时用脚本一键建立与登记（脚本**只在文件不存在时创建**，不覆盖已有索引）：

```bash
python {baseDir}/scripts/archive_tool.py init        [目录] --title "项目名"
python {baseDir}/scripts/archive_tool.py add-ref     <素材文件> [目录] --note "说明"
python {baseDir}/scripts/archive_tool.py deliver     <成品文件> [目录] --name "交付物名称" [--major]
python {baseDir}/scripts/archive_tool.py add-draft   <草稿文件> [目录] --note "说明"
python {baseDir}/scripts/archive_tool.py list-drafts [目录]
python {baseDir}/scripts/archive_tool.py plan-rename [目录] --name "交付物名称" [--only "核心名"] [--glob "*.md"]
python {baseDir}/scripts/archive_tool.py verify      [目录]
```

- `deliver` 自动算出下一个更N、自动改名、自动把上一版移进 `_archive/`、自动更新索引——**不要手工拼文件名**。
- `plan-rename` 给**已经存在的历史文件**生成改名方案，**只预览不改动**。参数含义：
  - `--name`：这批文件改完之后叫什么（必填）；
  - `--only "核心名"`：目录里混着多个交付物时，指定只处理其中一组；
  - `--glob "*.md"`：只看某类扩展名（默认按 `DOC_EXTS` 过滤文档类）。
- `verify` 只读体检：散落文件、缺更N 前缀的交付物、内容重复的素材、归档断号、草稿堆积。

### plan-rename 的三道安全检查

整理旧文件夹时最容易闯的祸，是把**不同交付物**混编成一条更新链。工具有三道闸：

**① 核心名残片拦截。** 文件名与既有约定差别太大时，解析出来的核心名可能退化成
`2`、`7-` 这类残片。此时工具**直接报错退出**（exit=4），列出可疑文件，等你人工
说明它属于哪个交付物——而不是猜一个名字生成 `更01-2-20260912.md`。
判据：解析结果为空、纯数字、纯符号、或单个字母，都视为不可信。

**② 归属校验。** 按核心名分组后，若出现多个不同的交付物而调用方没给 `--only`，
工具**拒绝执行**（exit=3），把分组清单打出来，要求逐组单独处理。
理由：把《AI教室建设与合作模式》改名成《AI教育厂商调研总结报告》，是在
**篡改文件归属**——文件内容没变，但它的身份被换了。这类改动不可逆，宁可多问一句。

**③ 修订分组。** 同一次修订常常同时存了 md / html / docx 三份，它们
**stem 相同、只差扩展名**，属于同一次修订，**共用同一个更N**；stem 不同才递增序号。

> 为什么不用修改时间聚类：批量另存时，同一批文件的 mtime 会差几秒到几分钟。
> 阈值设 120 秒会把两次独立修订并成一更；设 10 秒又会把同一次修订切成 更32 / 更35 / 更36。
> 任何固定阈值都会犯错，所以改用**文件名结构**判断——这是确定性的。
> mtime 仍参与，但只用来给各组**排序**（旧→新），不参与分组。

### 整理既有文件夹时

用户手上的旧文件夹往往长这样：同一份报告散着多个版本、部分带 `1-` / `2-` 前缀、部分带 `-前` 后缀、还有无前缀的裸名；**而且同一个文件夹里常混着好几个不同交付物**。整理流程固定为四步，**顺序不能反**：

1. 先跑 `verify` 摸清现状，让用户看到散落与重复的全貌；
2. 跑 `plan-rename`（**不带 `--only`**）——若目录里混着多个交付物，工具会分组列出来，
   据此确认这批文件到底分属几个交付物；
3. 按组分别跑 `plan-rename --only "核心名" --name "核心名"` 出方案，
   **把清单完整贴给用户确认**；
4. 用户确认后才动手，且必须先备份、分批执行（每批 ≤10 个）。

> 第 3、4 步之间不能跳过。文件名一旦改乱，用户原有的记忆锚点（"我记得那份叫 xxx"）就失效了，找回成本很高——所以宁可让用户多看一眼清单。

**每个交付物单独一条更新链。** 不同交付物的更N 各自从 更01 起算，不共用计数器；
也**不存在**「把 A 报告改名成 B 报告」这种操作——那是篡改归属，工具会拒绝。

**遇到解析不出的文件名，停下来问。** 若工具报 exit=4 并列出几个文件，说明它们的命名
与现有约定差得太远，机器猜不准归属。此时**不要自己替用户决定**，把文件名列出来，
问清楚各属于哪个交付物，再重新出方案。

用户已有既定目录习惯时，**以用户的目录为准**，只借用「附件区 / 产出区 / 草稿区」的语义与「更N」命名，不强行搬家。

### 版本策略：增量迭代，而非多文件爆炸

- 每次修改交付物，**只递增更N 与版本号**，同一交付物在 `deliverables/` 始终只有一份当前版；
- 旧版本移入 `deliverables/_archive/` 并在索引留痕，**不生成一堆独立的零散文件**；
- 索引里交付物主表是「当前状态表」（一个交付物一行，记最新的更N 与版本），历史迭代记在「历史归档交付物」小节，两者分开；
- 更N 是**交付物级别**的计数器：`更01` → `更02` → `更03`，每次迭代 +1，与 `v主.次` 同步推进但含义不同（更N 讲顺序，版本号讲改动幅度）。

### 精简原则：严控存档对象

> 长期归档**只保留两类**：原始素材 + 正式定稿交付物。
> 所有临时草稿、试错片段、多版备选文案，**默认不保存、不纳入备份**。

### 去重规则

存档前自动校验内容指纹（SHA-256）：

- 检测到重复原始文档，**只保留一份，拒绝重复备份**；
- 同名不同内容的文件不会被误判为重复，会加指纹后缀区分；
- 同一交付物重复交付同名版本时，就地更新而不再新增行。

## 迭代与调用逻辑

| 场景 | 动作 |
| --- | --- |
| 新任务启动 | **清空本次产出区**；附件索引可按需继承历史归档素材 |
| 迭代修改 | 更新【本次产出区】内容；旧交付物归档，`更N` +1，版本号 +1 |
| 新增素材 | 追加到索引**末尾**（对应小节内），原有索引保留不动 |
| 任务切换 | 保留附件索引，在标记里写明哪些附件不再参与当前任务 |
| 用户纠错 | 旧的错误结论不删，随历史版本一起归档，索引说明里标注原因 |
| 整理旧文件夹 | 先 `verify` 摸现状 → 再 `plan-rename`（不带 `--only`）确认有几个交付物 → 按组 `--only` 出方案 → **用户确认后**才分批改名 |
| 任务完成 | 整套结构可直接交给归档脚本，按目录规范落地成本地文件并更新总索引 |

## 禁止行为清单

❌ 自动生成大量中间草稿、备选方案，造成文件泛滥
❌ 重复保存同一份原始参考文档
❌ 素材内容和交付正文穿插混写
❌ 在产出区粘贴大段附件原文
❌ 无规则命名文件、文件散落在根目录
❌ 交付物文件名不以「更N」开头，或用 `更1`/`更2` 这种不零填充的写法
❌ 归档时重排旧文件的更N（`更02` 进归档后必须仍是 `更02`）
❌ 不写附件索引就直接输出成品
❌ 删除附件备份区里已归档的历史素材、旧版本产出
❌ 重排/复用已分配好的附件编号
❌ 未经用户确认就批量改名或整理用户已有的文件夹
❌ 把不同交付物混编成一条更新链，或把一个交付物的名字改成另一个（篡改归属）
❌ 解析不出核心名时自作主张猜一个名字，而不是停下来问用户

## 交付前自查

1. 【附件备份区 - 索引清单】是否存在，且排在成品之前？
2. 索引里的每条是否都有编号 + 名称 + 说明 + 标记？
3. 本轮新增附件是否追加在末尾，而不是插进中间？
4. 交付物文件名是否符合 `更NN-名称-YYYYMMDD.ext`？序号是否零填充两位？
5. 上一版成品是否已归档（`_archive/` 或索引中的 `历史产出 vX.Y（已归档）`），且序号**未被改动**？
6. 【本次产出区】正文里有没有大段抄来的原文？有就删掉，换成 `参考附件N` 的引用或自己的表述。
7. 有没有产生多余的草稿 / 备选文件？有就并入 `tmp_drafts/` 或直接不落盘。
8. `---=== 分割线 ===---` 是否原样保留？

## 自我进化机制（遵循 `cyx-skill-evolution` 通用条款）

**本技能不是一次写死的。** 用户拿本技能管理文件时提的每一条修改意见，都可能是适用于**所有后续交付**的归档规则；把它挑出来写回本文件，本技能才会越用越准。判定、留痕、回退规则见 `cyx-skill-evolution`。

**触发**：用户对命名、分区、归档、目录结构提意见（「命名要改」「这个不该存档」「目录层级太多」）；同一类意见出现 ≥2 次 → 从「建议」升为强约束；我主动发现规则之间打架（如命名规范与归档规则冲突）→ 不等指令当场修。

**落点映射**：

| 反馈类型 | 典型原话 | 改本文件哪一节 |
|---|---|---|
| 命名规范 | 「文件名要能看出先后」「`更1` 要补零」 | 「文件命名规范」+「交付前自查」第 4 项 |
| 分区与索引 | 「索引缺标记」「附件要排在成品前」 | 「两个区」+「强制输出格式」+ 自查 1–3 项 |
| 三级目录 | 「目录太多 / 太深」「该放哪一级」 | 「三级目录规范」+「plan-rename 的三道安全检查」 |
| 归档与去重 | 「这份不该留」「重复存档了」 | 「版本策略」/「精简原则」/「去重规则」+「禁止行为清单」 |
| 处理既有文件夹 | 「帮我整理下这个文件夹」 | 「整理既有文件夹时」（先只读体检 → 出方案 → 确认后分批改） |
| 与其它技能的衔接 | 「和 xx 技能的命名口径不一致」 | 「迭代与调用逻辑」+ 文末分工节 |

**沉淀后必做**：① 规则与「交付前自查」**两处同步**；② 改名/归档类规则尽量写成可机械执行的判据（能写脚本的写脚本）；③ 在 `cyx-skill-evolution/references/feedback-log.md` 追加一行（本技能无自带账本，写通用账本）；④ 一句话告知用户「这条记进 cyx-doc-separate 了」。

## 一句话启用指令

> 启用 cyx-doc-separate 文档分区与精简归档 Skill，按规则隔离素材与交付物，精简归档，控制文件数量。

需要在别的工具（如豆包自定义系统指令）里复用规则时，用这段精简版：

> 启用 cyx-doc-separate｜文档分区与精简归档 Skill。
> 【附件备份区】存放原始素材、历史定稿交付，仅维护索引清单，不粘贴全文；同一份素材只保留一份，临时草稿默认不归档。索引格式：文件名｜简要说明｜标记【原始素材 / 历史归档交付物】。
> 【本次产出区】仅存放本次任务唯一定稿交付物，默认不输出中间草稿；迭代更新时旧版本移入附件备份区，不新建零散文件。引用素材仅标注参考附件编号，禁止大段原文嵌入交付正文。
> 输出固定结构：先输出【附件备份区 - 索引清单】，然后用 ---=== 分割线 ===--- 分隔，再输出【本次产出区：交付物名称｜更N · 版本】与成品正文。
> 归档规则：长期仅保留原始素材 + 定稿交付物；本地文件固定放入 reference/、deliverables/、tmp_drafts/ 目录；交付文件命名 更NN-名称-YYYYMMDD.ext（序号零填充两位，如 更01、更10）；归档时序号原样保留、不重排；自动去重，不重复备份原始文档；tmp_drafts 内临时文件定期清理。
> 命名要求：「更N」前缀放文件名最前，让文件管理器按名称排序即可看出更新先后，取代 -前 / -旧 / -副本 / -final 等手工后缀。
> 禁止：产出大量零散草稿、重复存档原文、素材与交付内容混写、无规范命名、未经确认批量改名。

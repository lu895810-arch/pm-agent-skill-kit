# 产品功能规划拆解（cyx-strcuture-need）

## Purpose（目的）

把「一份已存在（或规划中）的产品 / 平台」——基于它的实际能力、界面与材料——**组织成一份结构清晰、可直看、可讲、可立项评审的《产品功能规划》**。

这份规划是一份**单文件暗色科技风 HTML**：老板 / 产品 / 研发打开就能看、产品能照着立项讲、研发能照着排期。它来自一份真实跑通的稿子（LibTV AI 视频创作平台产品功能规划 V1.0），那份稿子做对的三件事，也是本 skill 的交付标准：

1. **先抽象再落地**——几十个功能先归纳成「四层架构」，再落为「N 个核心模块」，审阅者不会在细节里迷路。
2. **优先级贯穿全文**——模块清单、逐模块展开、优先级矩阵、MVP、路线图五处都带 P0–P3，且彼此不打架。
3. **规划能落地**——MVP 主线 + 验收 KPI + 分阶段路线图 + 核心数据对象 + 北极星指标，半年后的人还能看懂当初怎么定的。

**与既有 cyx 技能的分工（不重复造）**：

| 事项 | 归谁 |
|---|---|
| 单文件暗色科技风 HTML 模板、组件类、徽章自动着色、进度条 / 导航 / 返回顶部 | **本 skill** |
| 四层架构 / 模块拆解 / 优先级矩阵 / MVP / 路线图 / 数据对象 / 指标风险 的**拆解手法与骨架** | **本 skill** |
| 语言纪律（去 AI 味、通俗、逻辑闭环、衔接流畅、跨格式语言总纲） | `cyx-md-style` + `~/.workbuddy/MEMORY.md`「语言总纲」 |
| 视觉纪律（暗色科技风配色、反塑料味、去 emoji） | `cyx-html-style` |

## When to use（何时触发）

**触发**：

- 用户要「做一份产品功能规划 / 产品架构拆解 / 功能模块清单 / 产品规划文档」，并希望产出一份能直接打开看的单文件 HTML。
- 用户手里有产品白皮书、官网、教程、界面截图、旧版方案，要把它们收敛成一份**带四层架构、模块拆解、优先级矩阵、MVP 与路线图**的规划。
- 用户说「把这款产品拆成模块」「帮我做份产品规划，像 LibTV 那份那样」「定一下 MVP 范围和路线图」。
- 用户要的是「能看、能讲、能立项评审」的规划架构，不要求 EARS 工程级派工粒度。

**不触发**：

- 直接写「每条带验收要点的需求文档 / PRD」→ `cyx-summary-need`；重型十章 EARS PRD → `cyx-ears-need`。
- 追「为什么做成现在这样、每版解什么矛盾」的演进成因 → `cyx-original-need-md`。
- 从 0 到 1、连产品都还没定义、要选框架出画布 → `ai-product-methodology`。
- 纯市场调研、不涉产品内部规划 → `cyx-research-report`。

## 零、适用范围与跨域适配（先读这段再动手）

**通用性判据**：本 skill 交付的是「把产品能力组织成可立项评审的功能规划」的**规划逻辑**，不是某一行的业务知识。只要一个产品同时具备这三点——「可被拆解的功能集合 + 需要排优先级 + 需要讲清 MVP 与路线」——骨架就成立，不挑行业。

**完全通用的部分（换产品不用改）**：

- 十步推进链的顺序与逻辑关系（定位 → 四层架构 → 模块清单 → 逐模块 → 横切 → 矩阵 → MVP → 路线图 → 数据对象 → 指标风险）
- 优先级纪律（P0–P3 单调降序、矩阵 ✅/○/—、清单表 ↔ 矩阵 ↔ MVP ↔ 路线图 四处自洽）
- MVP「只保主链路 + 暂不纳入 + 验收 KPI」、路线图「V0.1→V3.0 对应 P0→P3」
- 核心数据对象的写法（对象链 + 横切系统围绕对象搭）与「先冻结对象字段再开发」的纪律
- 北极星指标 + 风险（等级 + 对策）

**需要按行业重贴标签的部分**（模板里的示例名是 AI 内容生产平台的口味，换业务要换，但逻辑不动）：

- **四层架构的层名**：模板给的是「创意 / 生产 / 工程 / 流通」，是内容生产平台的视角。换行业要重命名每层的「核心问题」与「典型包含」，但层逻辑不变——每层仍只回答一个不重叠的根本问题。
- **横切系统**：模板列了「Agent / 工作流 / 模型路由（Router）/ API / 专业虚拟摄影棚」。其中「模型路由」「专业虚拟摄影棚」是 AI / 内容专用；非 AI 产品换成「权限 / 计费 / 第三方集成 / 审计日志 / 租户隔离」等。
- **模块清单的示例模块（04–06 图片 / 视频 / 音频）**：媒体生产专用，其他产品直接删，换成自己的核心模块。
- **核心数据对象链示例（Story / Character / Shot / Video）**与 **KPI 卡示例（画幅 / 成片）**：媒体专用，替换为本行业对象与验收口径。

**跨域层名映射（参考，不强制）**：

| 产品类型 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| AI 内容生产平台（默认） | 创意层 | 生产层 | 工程层 | 流通层 |
| B2B SaaS | 获客 / 试用层 | 业务处理层 | 配置 / 集成 / 权限层 | 续费 / 生态层 |
| 开发者工具 | 接入 / 上手层 | 编排 / 执行层 | 调试 / 部署 / 可观测层 | 插件 / 社区层 |
| 电商 / 交易 | 浏览 / 决策层 | 交易 / 履约层 | 库存 / 风控 / 物流层 | 复购 / 分销层 |
| 硬件 / IoT | 配网 / 绑定层 | 控制 / 数据采集层 | 固件 / 联动 / 规则层 | 服务 / 订阅层 |

**一句话**：骨架通吃，标签各家填。拿不准层怎么叫时，先守住「每层只答一个根本问题、四层不重叠」这条判据，名字是其次。

## 一、产出物骨架（十步推进链）

文档顺序固定，是一条从「这产品是什么」推到「下一步怎么排期」的链，**段不要少、不要乱序**。

```
【定位与价值主张】
  1. 核心定位        一句话定位 + 产品要回答的核心问题 + 解决的核心痛点
  2. 完整主流程      主流程 ASCII（输入 → 各环节 → 成片 → 复用），底层支撑单列一行
  3. 真正的差异化竞争力  基础能力（迟早人人都有）vs 真正拉开差距的东西（串成完整流程的能力）
【四层产品架构（总纲）】
  四层：创意层 / 生产层 / 工程层 / 流通层；每层一句话核心问题 + 包含模块；用 layerbar 视觉条
【核心模块功能清单】
  N 个一级模块表：模块｜核心功能｜定位｜优先级（按 P0→P1→P2 单调降序，不逆序混排）
【逐模块功能展开】
  每个模块一小节：核心入口/功能分组表（带 P0/P1/P2）+ 关键机制说明（每张表后一条 .note）
【横切系统】
  Agent / 工作流 / 模型路由（Router）/ API 开放平台 / 专业虚拟摄影棚 等跨模块系统
【功能优先级矩阵（P0–P3）】
  模块 × 阶段（P0 核心可用 / P1 差异化 / P2 专业生产 / P3 平台化），✅/○/— 标记（JS 自动着色）
【MVP 范围建议】
  MVP 主线 + 暂不纳入 + 验收标准（KPI 卡：步数 / 链路 / 画幅 / 版本）
【分阶段路线图】
  V0.1→V3.0，每版本：目标 + 关键交付
【核心数据对象与关键系统】
  核心对象链（User→Project→…→Publish）+ 关键横切系统（版本/任务/搜索/安全/适配发布/协作）
【北极星指标与风险】
  北极星与关键指标表 + 风险与合规（等级 + 对策）
────────────────────────────────────────────
【附录】文档口径与来源
  口径与边界（内容基线 / 口径冲突 / 推断怎么标 / 文档定位）+ 参考来源 + 变更记录
```

**逐段写什么、必填什么——见 `references/structure-playbook.md`。每写一段前先翻对应小节。**

**数字必须闭合**：头部 KPI（模块数 / 层级数 / P0 主链路状态 / 待确认数）↔ 正文实际计数 ↔ 附录条目数，三处对得上。

**骨架里有「可选」——判据是「手上有没有对应材料」，没有就整块不写**：若产品没有「专业虚拟摄影棚」这类高端能力，第 5 章对应小节整段不写；若产品尚不需对外 API，第 5 章 API 小节不写。骨架主体（1–10 章）必写。

## 二、模块与编号公约

核心模块（第 3 章）按**模块**分组，每个模块一个序号 + 主题名，逐模块展开时也用同一序号。

**模块数通常 6–10 个**：太少说明漏了横切能力（资产 / 社区 / 商业化最常被漏），太多说明颗粒度太细要合并。模块按**用户做事的自然顺序**或**产品入口顺序**排，不按技术依赖排。

| 通用位置 | 主题 | 通用要回答的问题 |
|---|---|---|
| 模块 01 | 首页 / 创意中心 | 用户不知道从哪开始时，第一步落在哪？降低门槛的入口 |
| 模块 02 | 创作工作台 / 画布 | 专业用户精细控制的生产核心（通常 P2，不进 MVP） |
| 模块 03 | 故事 / 剧本 | 长内容怎么结构化、怎么变成角色与分镜资产 |
| 模块 04 | 图片创作 | 视觉素材怎么生、怎么改 |
| 模块 05 | 视频创作 | 视频怎么生、怎么改、怎么理解（理解→生成→编辑） |
| 模块 06 | 音频创作 | 声音怎么生、音色怎么绑定 |
| 模块 07 | 后期 / 剪辑 | 有没有剪辑，决定是「素材工具」还是「视频平台」 |
| 模块 08 | 资产 / 社区 / 商业化 | 内容怎么沉淀、流通、变现 |
| 模块 N | 按产品实际补 | 行业特有的模块（如「专业虚拟摄影棚」「出海 / 转绘」） |

**其他编号**：

| 对象 | 格式 | 备注 |
|---|---|---|
| 模块 | `模块 01` `模块 02` … 连续阿拉伯数字 | 清单表与逐模块小节共用同一序号，不跳序不倒序 |
| 功能分组项 | `A1` `A2` … `B1` `B2` … | **每个模块一个字母前缀，按模块顺序从 A 连续分配**；表内单独 `编号` 列，不与能力名混写；模块内数字 1,2,3… 连续递增，不跳号不倒号 |
| 优先级 | `P0` / `P1` / `P2` / `P3` | P0 = 主链路闭环必须；P1 = 差异化；P2 = 专业生产；P3 = 平台化。**排序纪律：清单表与逐模块表内，需求行必须按 P0→P1→P2→P3 单调降序；增量补行要插进对应优先级段，别顺手加到表尾。** |
| 风险 | 无固定编号 | 以等级（高/中/低）+ 对策呈现；若需编号，用 `风险-1` 等显式标签，避免与模块 / Roadmap 字母前缀混淆 |
| 待确认 | `B-1` | 编号连续，状态三档：`待确认` / `部分确认` / `已确认` |
| Roadmap / 迭代池项 | `R1` `R2` … | 不属于当前模块、但需在 MVP/路线图/风险说明中引用的后续项，统一用 `R` 前缀，避免与模块 A–H 混用 |
| 矩阵标记 | `✅` / `○` / `—` | ✅ = 该阶段核心可用；○ = 该阶段部分/弱；— = 该阶段不做；**纯文本写，JS 自动着色**，不手写徽章 HTML |

**优先级判据**：一条功能删掉后，「从输入到成片（或产品的核心产出）」的主链路还走得通吗？走得通 → 不是 P0。

## 三、四层架构怎么归纳（本 skill 的核心手法）

几十个功能不逐个列，先按「每层解决一个根本问题」归成四层。四层不是技术分层，是**用户视角的价值分层**：

| 层 | 核心问题 | 典型包含 |
|---|---|---|
| L1 创意层 | 我要做什么？ | AI 创意助手、剧本、故事、角色、模板 |
| L2 生产层 | 怎么把创意变成素材？ | 图片、视频、音频、分镜、模型 |
| L3 工程层 | 怎么规模化、高质量生产？ | 画布 / 节点、工作流、Agent、资产管理、一致性、批量 |
| L4 流通层 | 怎么让内容持续生产与流通？ | 社区、模板市场、资产市场、API、会员、算力 |

**判据**：这一层如果被删掉，用户侧缺的是「不知道做什么」「做不出素材」「做不快/做不准」还是「做出来没地方流通」？四层各答一个，不重叠。PRD 拆解时所有功能都按这四层归口。

**差异化竞争力（第 1.3 节）不要省**：明确点出「哪些能力迟早会变成人人都有的基础能力（单点生成），哪些才是真正拉开差距的东西（把基础能力串成完整流程的系统能力）」。这份判断是后续优先级与 MVP 取舍的依据。

## 四、优先级矩阵与 MVP / 路线图的关系（闭环）

三处都用 P0–P3，且必须自洽：

1. **清单表（第 3 章）**：给每个模块一个总体优先级（P0/P1/P2），按降序排。
2. **矩阵（第 6 章）**：把每个模块拆到「P0 核心可用 / P1 差异化 / P2 专业生产 / P3 平台化」四个阶段列里，标 ✅/○/—。**矩阵的列向之和必须与清单表的模块总体优先级一致**（一个模块总体 P0，它就该在 P0 列有 ✅，而不是跑到 P2 列才出现）。
3. **MVP（第 7 章）**：只保「矩阵 P0 列 ✅」串成的主链路闭环，其余一律「暂不纳入」。
4. **路线图（第 8 章）**：V0.1→V3.0 对应 P0→P3，每版本的关键交付必须能在矩阵里找到对应 ✅/○。

**闭环检验（每写完一处抽一次）**：头部 KPI 的「P0 主链路状态」↔ 清单表 P0 行数 ↔ 矩阵 P0 列 ✅ 数 ↔ MVP 主线覆盖的模块，四处对得上。

## 五、核心数据对象（决定产品是否成立为「系统」）

第 9 章必须画一条**核心对象链**（`User → Project → Story → Character → Scene → Asset → Storyboard → Shot → Generation → Timeline → Video → Publish` 这类），并点出 3–5 个核心对象（如 Project / Asset / Storyboard / Shot / Generation）。

**纪律**：版本、任务、搜索、版权溯源、协作这些横切系统，全都绕着核心对象搭。建议规划阶段先把核心对象的字段与关系定死，别等做了一半再改——这是产品从「工具」升级为「系统」的关键，也是和第 7 章 MVP「最小资产即可、复杂管理留 P1」呼应的地方。

## 六、语言与视觉纪律（遵循全局设定）

本 skill 的模板只管「结构骨架 + 渲染长什么样」，文字怎么写遵循全局 cyx 设定，**不在此重复维护**：

- **跨格式语言总纲**（`~/.workbuddy/MEMORY.md`「语言总纲」，最高优先级）：一切文字产出都要满足**通俗易懂、专业严谨、叙事逻辑闭环、段落衔接流畅、去 AI 味**五条。
- **内容侧写法**：`cyx-md-style` 的「语言规范 / 逻辑与口径」（先事实后判断、结论有证据、术语给白话定义、宁缺毋造、无 AI 过渡填充）。
- **视觉侧写法**：`cyx-html-style` 的「色彩与视觉风格 / 反塑料味」（暗底为主、高饱和色只作点缀、标题用总结性实体名词、不堆科技感符号）。

**落到本模板的硬约束（摘要，具体以全局 skill 为准）**：

1. 标题写实体名词（「核心定位」「四层产品架构」），不写「一句话结论 / 核心要点 / 机制推演」这类空标签与修辞动作。
2. **来源口径冲突处理**：同一事实在不同材料里说法不一致时，**不在正文中硬凑统一口径**；分别标注来源与差异，并挂 B 编号待确认。宁可多一条待确认，也不自信生成一个看似统一的数。
3. 不用 emoji 装点，不写「赋能 / 抓手 / 闭环 / 干货 / 底层基建 / 护城河」等空话（「闭环」若指具体流程可保留，但优先用「串成一圈 / 主干走通」）；不用「首先/其次/最后」「综上所述」「值得注意的是」过渡填充。
4. 术语首次出现给一句人话解释（是什么 + 为什么叫这个名），不拿同义词当解释。核心概念（Agent、节点、分镜、资产一致性、Router）保留，因为是该产品规划的支柱，且在上下文已有出处。
5. 每个判断有依据、每个风险有对策、每个待确认有责任人——不写悬空待定。
6. **头部只写产品摘要，口径与变更进附录**：`.kick` 写产品核心摘要（面向谁 + 输入什么 + 自动产出什么）；来源范围、口径归属、推断怎么标 → 附录；变更流水只在附录一处。
7. **证据链不留白**：判断后面跟依据（材料 / 界面观察 / 口述），风险后面跟对策，待确认后面跟责任方与编号。
8. **写正文时只写纯文本**：优先级写 `P0` / `高` / `待确认`，矩阵写 `✅` / `○` / `—`，**不要手写徽章 HTML，也不要写 emoji**——JS 会自动着色。

## 七、模板用法（执行顺序）

### Phase 0 — 定调（先问，别猜）

缺信息就问，一次问清：**产品名与形态（Web/App/硬件/服务）· 客户形态（B/C/双端）· 已有能力清单或材料（白皮书 / 官网 / 教程 / 截图）· 当前阶段（已上线 / 规划中）· 首发场景（只定一个）· 核心问题（用户现在用什么替代、代价是什么）· 能力边界（自研 vs 接入第三方）· 交付形态（只要 HTML，还是也要 MD/Word）**。

用户只有素材、答不上来时，**先按常识给一版假设并显式标注「假设待确认」**，进入 Phase 1，不要卡住不动。

### Phase 1 — 复制模板

```bash
cp {baseDir}/assets/template.html <你的产出路径>.html
```

模板已内联全部 CSS 与 JS，改内容即可，无需外链。

### Phase 2 — 填定位与四层架构

先写第 1 章（核心定位 / 主流程 / 差异化竞争力）与第 2 章（四层架构 + layerbar），确定全篇基调。

### Phase 3 — 建模块地图

按第 3 章挑模块、起名（序号 + 主题），画一张「模块 → 核心功能 → 定位 → 优先级」草表。**优先级列必须按 P0→P1→P2 单调降序**。先给用户过一眼再往下写。

### Phase 4 — 逐模块展开

按模块写，每个模块：核心入口说明 + 功能分组表（带优先级）+ 关键机制（每张表后跟一条 `.note`）。**P0 模块的功能表要能串成主链路。**

### Phase 5 — 横切系统 + 优先级矩阵

写第 5 章跨模块系统；第 6 章矩阵按「第 4 章模块 × P0–P3 阶段」填 ✅/○/—，且与清单表、MVP 自洽。

### Phase 6 — MVP + 路线图 + 数据对象 + 指标风险

第 7 章只保矩阵 P0 列 ✅ 串成的主链路，配验收 KPI 卡；第 8 章 V0.1→V3.0 与 P0–P3 对应；第 9 章核心对象链 + 横切系统；第 10 章指标表 + 风险（等级+对策）。

### Phase 7 — 附录台账

待确认清单（**从正文把所有「待确认」抓出来汇总，一条不落**）→ 参考来源（每条来源写明「用途」）→ 口径与边界 → 变更记录。

**附录来源红线**：只列用户提供的**原始材料**（白皮书、官网、教程、截图等）。同空间其他衍生文档（如 PRD、旧版规划）不得作为事实来源，避免循环引用。

### Phase 8 — 机检与交付

- 用浏览器打开模板自测：进度条随滚动、顶部导航锚点可达、优先级单元格与矩阵 ✅/○/— 自动变徽章、返回顶部按钮出现。
- 点一遍导航的**每个**链接，确认锚点都存在。
- **闭环自检**：头部 KPI ↔ 正文计数 ↔ 矩阵 P0 列 ✅ 数 ↔ MVP 主线覆盖模块，四处对得上；清单表优先级列无逆序。
- 过第 8 章自查清单。
- 交付物按 `cyx-doc-separate` 命名与分区。

## 十、自我进化机制（遵循 cyx-skill-evolution 通用条款）

> **上游通用条款**：判定、留痕、回退的共性规则见 `cyx-skill-evolution`；本节是它在产品功能规划场景的落地。

**技能不是一次写死的。** 本 skill 内置「交付后自动回扫 → 判定通用性 → 归类 → 落盘 → 告知」的自主进化闭环：用户就功能规划提的每一条修改意见，都会先改当期产物，再自动判定是否属于可复用方法论；若是，则同步修正 `SKILL.md` 正文、`references/structure-playbook.md`、`assets/template.html` 示例与第九节自查清单，让下一次同类规划默认 avoid 同一问题。通用项写回本文件与模板，本 skill 才会越用越准。

### 10.1 触发时机

- 用户对**结构 / 骨架 / 编号 / 视觉**提意见（「少一层」「边距太窄」「模块顺序不对」「矩阵怎么标」）。
- **同一类意见反复出现（≥2 次）**——最强信号：不是当期文档的问题，而是默认写法错了，要升为强约束。
- 每完成一次交付就过一遍（哪怕用户一句意见都没提）——按 10.6 回扫本轮交互。

### 10.2 落点映射

| 代号 | 反馈类型 | 典型原话 | 落点 |
|---|---|---|---|
| D 结构与层次 | 章节结构 | 「少一层」「四层该改成三层」「模块该单独成章」 | 一 + `references/structure-playbook.md` |
| D 结构与层次 | 编号、优先级与台账 | 「编号和能力名混在同一栏」「A/G 字母混用」「模块内编号乱序」「矩阵和清单对不上」 | 二 + 四 + 九（自查） + `references/structure-playbook.md` 第 4 章「功能分组表编号纪律」+ `assets/template.html` 示例 |
| F 排版与视觉 | 呈现 | 「太像 AI 生成的」「边距」「layerbar 颜色」 | `assets/template.html` 的 CSS + 六（指向 cyx-html-style） |
| B 遣词与命名 / E 术语 | 语言与措辞 | 「太啰嗦」「看不懂」「逻辑跳」 | 六（指向 cyx-md-style / 语言总纲） |
| A 事实与依据 | 来源与口径冲突 | 「以这五份资料为依据」「不知道的宁可不写」 | Phase 0 / Phase 7 + 九（自查） |
| G 流程与命令 | 工具与执行 | 「这个命令跑不通」「复制模板失败」 | Phase 1 模板路径 |

### 10.3 落盘纪律（三不写）

1. **不与已有规则重复**：同类已在 → 就地强化，不新起一节。
2. **不写死具体数值**：写「判据 + 判定方法」，不写具体像素/模块数（会再变）。
3. **写不成判据的模糊直觉不进文件**：要么落成模板 CSS/JS 改动，要么落成自查清单一项。

### 10.4 沉淀后必做

1. 在 `references/feedback-log.md` 追加一行：`日期 / 原话节选 / 类别 / 落点 / 处置`。
2. 同类 ≥2 次 → 对应条目加粗升为强约束，并同步第九节自查清单。
3. 一句话告知用户：「这条我记进 cyx-strcuture-need 了，以后默认这么做。」——方便他当场纠正。
4. **回扫落点清单**：`SKILL.md` 正文、`references/structure-playbook.md`、`assets/template.html` 的示例、第九节自查清单。改一处必须核其余三处。

### 10.5 规则也会过时：允许回退

用户推翻某条 → ① 改对应条目，**标注适用边界**而非删除；② 在 feedback-log 追加「规则回退」；③ 查有无其他条目与之冲突。

### 10.6 每轮交付的自动回扫（不等用户开口）

1. **回扫本轮交互**：把用户从提需求到定稿说的话逐条过一遍，**尤其中途改口、推翻、补充的地方**。
2. **逐条判通用性**：只对当前这份文档成立（个案，只改当期产物），还是换个产品仍成立（通用，回写本技能）？
3. **归类**：按 10.2 表取一个主类代号。
4. **定落点并回扫四处**。
5. **落盘 + 告知**。
6. **没有可沉淀的就明说**：告诉用户「本轮没有需要写回技能的规则」。

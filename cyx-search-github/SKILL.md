# Cyx Search Github

在 GitHub 上系统调研一个产品类型的开源生态，产出能直接拿去搜、能直接拿去用的关键词清单和仓库参考。这是一套方法，不是一次固定搜索——目的是让"调研某类产品该怎么搜"可以复用到任何技术方向。

## 工作流总览

```
① 锁定目标 → ② 拆解模块 → ③ 生成关键词矩阵 → ④ 两条线执行搜索 → ⑤ 验证授权 → ⑥ 结构化交付
```

## Step 1：锁定目标

- 先确认用户要调研的**产品类型**（例：短剧平台、跨境电商独立站、AI 客服系统）。
- 问清两个问题：(a) 要可参考的完整产品/整站源码（学架构和交互）；(b) 要可复用的单点组件（播放器、支付、UI）。多半两者都要。
- 目标模糊时，先给 1~2 个假设方向让用户确认，别凭空铺开。

## Step 2：拆解模块

把目标产品拆成可独立搜索的**功能模块**。这一步是整个方法的核心——好关键词来自对产品的拆解，不是笼统搜产品名。

以短剧平台为例（演示拆法，不是唯一答案）：

- 播放端：竖屏滑动播放、HLS/m3u8 播放器、剧集切换、续播
- 客户端形态：微信小程序、H5、App（Flutter/RN）
- 商业化：付费解锁、订阅会员、虚拟币/钱包、广告解锁、分销 CPS
- 后台：内容管理、用户体系、数据统计
- 内容生产（可选）：AI 短剧生成、剧本、分镜

拆解时问自己：这个产品的用户会按哪些"零件"去搜？每个零件就是一个搜索维度。

## Step 3：生成关键词矩阵

对每个模块生成中英文关键词，至少 4 类：

1. **直接名称**：产品类型名（短剧平台 / short drama app）
2. **变体/别名**：同义词、垂直说法（短剧CPS / micro drama / mini drama）
3. **技术定位词**：栈相关的（uniapp 短剧 / flutter m3u8 player）
4. **商业词**：变现/分发相关的（短剧 分销 / dramabox clone / vod paywall）

关键词库模板见 `references/keyword-library.md`。新方向的词从中挑组合，搜的时候再补该方向特有的词。

## Step 4：两条线执行搜索

并行搜索，单轮不超过 3 个 query，避免重复搜同一信息。

### 线 A：整站 / 产品级调研（学架构与产品逻辑）

- 关键词用"直接名称 + 开源/源码/clone"，如 `短剧 源码`、`short drama app open source`、`dramabox clone`。
- 目的：找到能代表该产品完整形态的仓库，研究目录结构、技术栈、功能清单。
- 交付时标注：这类仓库多为"参考架构与交互，不直接生产用"。

### 线 B：组件级复用（找单点可用的开源件）

- 按 Step 2 的每个模块逐一搜，用"模块关键词 + 技术词"，如 `m3u8 player flutter`、`vertical video swipe`。
- 目的：为每个模块找 1~3 个候选组件，附适用平台（H5/RN/Flutter/小程序）。

### 工具怎么用（按我实际能用的来）

- **找仓库、拿 star、看目录结构**：优先用 GitHub 连接器（`mcp__github__search_repositories`），能按 star 排序、直接读仓库文件，比网页搜索稳。没连连接器时退到 `gh` CLI 或 WebSearch。
- **精读 README / 官方文档**：用 WebFetch 抓仓库 README 或 docs 页面，拿 star、技术栈、功能清单。
- **看实际代码和目录**：用 GitHub 连接器的 `get_file_contents` / 仓库浏览，别只看搜索摘要下结论。
- **中文整站/分销/小程序类**：很多实际托管在 Gitee，GitHub 搜不到时补一轮 Gitee（WebSearch 即可）。

对每个命中记录：仓库名、技术栈、功能、star、适合"参考"还是"复用"。

## Step 5：验证授权

复用前必须查 LICENSE：

- 很多"开源"源码标的是"仅可学习、商用需购买授权"（尤其中文整站短剧/商城类）。这是硬门槛，交付里必须标出。
- 用前读仓库 LICENSE 或 README 授权段，别只看"开源"两个字。

## Step 6：结构化交付

交付一份报告，固定结构：

1. **关键词矩阵**：按模块分列中英文关键词，用户能直接拿去搜。
2. **真实仓库清单（两张表）**：
   - 线 A 整站参考：仓库 + 说明 + star + 授权提醒
   - 线 B 组件复用：模块 + 推荐组件 + 适用平台
3. **选型与风险提醒**：哪些能直接复用、哪些建议自己写（通常是账号/钱包/支付/分账这类业务核心）、授权注意点。

报告交给 Lulu 时按"语言总纲"来：说人话、有依据、结论有推导、不写空话。

## 交付约束

- 所有仓库名、star、功能必须来自真实搜索结果，不编造不存在的仓库。
- 每个推荐尽量附来源链接。
- 引用搜索来源时标注来源。

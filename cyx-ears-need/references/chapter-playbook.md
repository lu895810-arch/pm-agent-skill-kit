# 逐章写法手册（chapter-playbook）

每章固定回答四问：**写什么 / 必填什么 / 用什么形态 / 常见错误**。
行业无关，表格里的字段名在不同行业可能需要换词，但**骨架不换**。

**全局约定：小节标题一律写实体名词。** 不带「（一页纸）」「（本版明确不做）」「（评审必读）」这类括注式自我描述，也不用「一句话 X」前缀；方法名与优先级标签（`（EARS）`、`（P1）`）例外。理由与判据见 `SKILL.md` 第 3 章第 5 条。

**全局约定：不写排版符号。** 章节引用写「1.5 节」，不写 §；范围号用 ～；装饰图形（方点、折角箭头）用 CSS 的 width/height + background 画，不写 ◆ ★ ▲ 这类字符；状态写 `阻塞 M0` / `已确认：结论` / `未启动——说明`，徽章由模板脚本注入，不写 emoji。理由与判据见 `SKILL.md` 第 3 章第 6 条。

## 审阅层

### 0.1 顶栏

**写什么**：版本徽章 + 状态徽章 + 阻塞徽章 + 一行摘要（日期 · 首发形态 · 核心手法 · 阶段）。

**形态**：`.header` 内三个 `.bdg`（`.b-v` 版本 / `.b-w` 待评审 / `.b-b` 阻塞）+ 右侧 `.hd-r` 一行。

**常见错误**：

- 只写标题不写状态——评审者不知道这份能不能签字。
- 阻塞徽章里写一堆细节，挤不下。**只写编号**：`M0 阻塞 B-3 / B-4`。

### 0.2 Hero（主名 + 文档类型行 + 定位 + KPI 元数据卡）

**写什么**：英文小标（`Product Requirements Document`）→ **产品主名**（一级标题，只放产品名，不放"产品需求文档"）→ **文档类型行**（`产品需求文档` + 一条向右渐隐的横线 + 线尾挂 `版本 · 日期`）→ **一段定位描述**（面向谁、是什么、做到什么程度、**不做**什么）→ 6 张元数据卡。

**为什么把文档类型从大标题里挪出来**：主名与"产品需求文档"两行大字叠排，字号相等、语义不对等，标题块头重脚轻；挪成主名下方的一行小标后，主名独享视觉重心，那一行小标 + 延展横线同时把版心左右拉通。

**形态**：`.hero > .hero-in > .hero-t`（左侧 2px 渐变导轨）内含 `.kick` / `h1` / `.tsub`；`.metas` 在 `.hero-t` 之外，横向铺满。

**元数据卡固定六张**（这是评审者第一眼看的）：

| 卡 | 内容 |
|---|---|
| 版本 | `V1.6` |
| P0 需求 | `25 + 1`（写清"+1"是什么，如"+1 条架构约束"） |
| 页面 / 模块 | `14 / 18`（MVP 交付数 / 总数） |
| 北极星 | 指标名 |
| 待确认 | `15 项` |
| 状态 | `待 M0 评审` |

**常见错误**：

- 定位描述只写"是什么"不写"不做什么"。**"不做"要在这一句里就出现**，它比"做什么"更能界定范围。
- 标题写成两行等重大字（主名 + 文档类型），甚至把文档类型放第一行——读者第一眼看到的是"这是一份什么文"，而不是"这是谁的需求"。
- 元数据卡只填版本与状态，空着 P0 体量、页面数、待确认数——这几张卡是数字闭合的头部锚点，空着会让第 5 组机检无从比对。
- 定位描述里给占位符两侧留空格（`的 {{产品形态}}`）——中文内容替换后就是多余的空白，模板里就不要留。

### 0.3 审阅议题（`.review`）

**写什么**：3–6 条，格式 `编号｜议题｜建议责任人`。

**必填**：编号、一行议题（含**要决策什么**，不是"讨论什么"）、责任人（可以多角色，如"研发 + 商务"）。

**形态**：`.review > .rv-grid > .rv`，每条 `.n` 放序号、`.t` 放议题、`.who` 放责任人。

**常见错误**：

- 议题写成任务（"完成供应商选型"）—— 议题是**当场要拍的决定**，写成"B-3 关闭：首批供应商清单与商务条款（≥2 家冗余）"。
- 责任人不写——会上就没法往下分。

### 0.4 文档信息表

**两列 `项｜内容`**，行要齐：

`文档名称` / `版本` / `编制日期`（含各版日期）/ `定位基线`（以哪份材料为准）/ `范围决策`（回指决策记录）/ `文档状态` / `关联文档`（含各文档的职责边界）

**必填**：**定位基线**与**关联文档**。

**常见错误**：关联文档只列名字不写边界 → 冲突时无仲裁依据。**必须写成**："页面级交互细节以《02_原型规格》为准；经营与合规就绪以《上线就绪清单》为准；冲突时以本文档为准。"

### 0.5 评审速览

**两列 `维度｜结论`**，维度固定（内容因产品而异）：

`核心定位` / `首发范围` / `MVP 内核` / `MVP 体量` / `明确不做` / `商业模式` / `北极星指标` / `阻塞项` / `并行启动` / `风险 Top3`

**必填**：全部十项。**注意"并行启动"**——那件"周期比开发还长、必须今天就动"的事（证照、采购、备案、供应商谈判）。这一项最容易被漏，也最容易导致项目延期。

**常见错误**：把速览写成摘要文的浓缩版（每个维度写三行）。**速览是列表，不是段落**：一个维度一行，超一行就是没写完。

### 0.6 目录

正文章 + 附录各一行，**括号里带二级小节名**。它同时是读者的地图与作者的完整性检查表。

## 1. 背景

### 1.1 问题定义

**三段式**：行业判断（大势 1 段）→ **痛点清单**（有序列表，每条 = 加粗短语 + 一句展开）→ **本产品的回答**（1 段，把产品主张浓缩成一句）。

**痛点清单的判据**：每条都要能被后文的需求条目"对得上号"。写 5 条痛点，正文里必须能找到对应解决它们的需求组。

**常见错误**：痛点写"效率低""体验差"这种不可验证的形容词。**要写机制**："一部短剧的生产需要在 5–8 个工具间来回切换，上下文反复丢失。"

### 1.2 市场论证摘要

**三列 `信号｜证据｜对本产品的含义`**。

**必填**：第三列必须下判断。开头用 `blockquote` 声明"详细论证见关联文档，此处仅列结论"（**不在 PRD 里重复论证全文**）。

### 1.3 竞争格局与差异化

**三列表格 `竞品｜关键能力｜对本产品的启示`** + **差异化定位声明**（无序列表，三条：定位 / 核心差异 / 明确不正面竞争的领域）。

**必填**：差异化声明必须包含**"明确不正面竞争的领域"**——只说"我很强"不构成差异化。

### 1.4 名词术语表

**两列 `术语｜定义`**。

**必填**：所有自造概念 + 有阶段性边界的概念。

**判据**：正文里凡有歧义可能的词，都要进这张表。定义里若含时点（"商业化后启用"），必须写明。

**常见错误**：术语表成了装饰（只放两三条通用词）。**它应该是文档里最长的一张表之一**——一份 PRD 通常 10–15 个自造术语。

### 1.5 决策记录

**四列 `编号｜决策项｜结论｜影响`**。

**必填**：

- 每条决策的"影响"列要写**它改变了哪些章节**（"新增 T1–T5；P18 扩展为…"）。
- **被后续决策覆盖的旧决策不删除**，在影响列注明"初版决策，后被 D-05 扩展"。

**常见错误**：把决策记录写成会议纪要（连讨论过程一起写）。**只写结论与影响**。

## 2. 产品定位与目标

### 2.1 核心定位

**一段话**，含：面向谁 + 产品形态 + 从什么到什么 + 四个以内的核心承诺。

模板：`面向 {客户} 的 {形态} {品类}：从 {A} 到 {B}，{承诺1}、{承诺2}、{承诺3}、{承诺4}。`

**常见错误**：写成 slogan（"让创作更简单"）。**承诺必须是可被需求验证的**——"角色不漂移"能对应到 B1/B3，"成本可核算"能对应到 H1a。

### 2.2 目标用户与画像

**四列 `画像｜典型特征｜核心诉求｜使用深度`**。

**必填**：

- 画像**编号**（`U0`/`U1`/`U2`…），后文用户故事直接引用 `作为 U2，我希望…`。
- "使用深度"列写清**主要用哪几个页面/模式**，这让画像落到实现层。
- 后置画像用 `blockquote` 说明（"阶段二引入 X 场景后新增 U4…"）。

**常见错误**：画像只有 1–2 个。**B 端产品至少 3 个**（决策者 / 执行者 / 协作方），否则协作类需求无处落地。

### 2.3 首发场景策略

**无序列表 2–3 条**：只开放哪个场景 + 其余场景的**置灰策略**（展示"规划中"并收集点击意向，为阶段二排期提供数据）+ 该场景对平台的**特殊要求**（并回指到已体现的需求编号）。

**常见错误**：场景收敛的理由不写。**"为什么只做一个"和"只做一个"同等重要。**

### 2.4 目标与业务目标

**三列 `维度｜目标｜度量`**。产品目标 3–6 条，业务目标 2–3 条。

**必填**：每条都有度量，且度量**指向第 7 章的指标**（写"目标值见 7.1 节"）。

**常见错误**：度量写"用户满意度提升"这种无法计算的东西。**度量必须是指标名 + 口径**。

### 2.5 北极星指标

**一段**：指标名（中英文全称）+ **为什么是它**（同时反映哪几件事）+ 回指指标树位置。

**判据**：好的北极星同时反映**激活、深度、商业潜质**三者中的至少两个。

### 2.6 非目标（本版明确不做）

**有序列表**，每条 = **明确不做 X + 理由 / 替代方案**。

**必填**：

- 至少一条写清**"预留了扩展路径"**（如"C 端扩展为后续版本目标：账号与数据模型已按 T6 预留，开放个人注册时无需数据迁移"）。
- 至少一条写清**"不作正面竞争"**。
- 若有本版不做但商业化/成长必须有的，写明**在哪个节点启用**。

**常见错误**：非目标写成"暂不支持"清单。**每一条都要有理由**——没有理由的"不做"会在下次评审会上被推翻。

## 3. 需求描述（EARS）

### 3.0 EARS 约定

**三列表格 `类型｜句式｜用途`**，五类：

| 类型 | 句式 | 用途 |
|---|---|---|
| Ubiquitous | 系统应始终…… | 全局约束 |
| Event-driven | 当……时，系统应…… | 主流程行为 |
| Unwanted | 如果……（异常），则系统应…… | 异常与故障处理 |
| State-driven | 在……（状态）期间，系统应…… | 状态内行为 |
| Optional | 在提供……（功能）的情况下，系统应…… | 可选能力（含阶段二/三特性） |

**章首再补一段**说明本组的展开程度：`P0 需求完整展开；P1/P2 需求给出主条目，细节评审后补全。`

### 3.x 需求条目（六段式）

每条 = `h4` 标题 + 无序列表六段。展开程度按优先级（见主文件 第 2 章第 3 条）。

标题格式：`{编号} {需求名}（{优先级}，{来源标注}）`

例：`A1 剧本/小说导入与结构化解析（P0）` / `T5a 用量统计与团队配额（P0，V1.4 自 T5 拆分，MVP 成本保护机制）`

**标题里要带**：编号、需求名、优先级、**来源**（新增/拆分/降级/后移 + 依据的决策编号）。

**六段**：

```
- 用户故事：作为 {Ux}，我希望 {动作}，以便 {收益}。
- EARS：
  - {4–6 条，五类句式混用}
- 验收标准：{可量化场景}。
- 关联页面：{P0X → P0Y}。
- 边界与异常：{失败/超限/冲突/空态处理}。
```

**每条 EARS 的判据**：能不能被测试同学直接转成一条用例？不能就重写。

**"关联页面"写"无（架构层）"也是合法的**——纯架构约束类需求没有界面。

**常见错误**：

1. **验收标准写成"功能可用"**——要写数字与场景（"10 万字剧本解析 ≤120s；实体列表可编辑；点确认后角色自动写入 P05/P06"）。
2. **EARS 全是 Event-driven**——没有 State-driven 与 Unwanted，说明异常与状态没想清。
3. **边界与异常写成"待定"**——可以写"以技术评审为准"，但要写明**谁的评审、什么时限**。

### 架构约束类需求

没有用户故事、没有页面，只有约束时，用：

```
- EARS（Ubiquitous，设计约束）：系统应采用……模型；……不应将 X 硬编码为唯一容器。
- EARS（Optional，后续版本）：在提供……的后续版本中，……应可……。
- 验收标准（本版）：{设计评审通过的具体检查点}。
- 关联页面：无（架构层）。
```

**价值**：这类需求不进 MVP 功能表，但进评审准入条件（"架构评审通过"）。**它是把"未来要扩展"变成"今天必须设计对"的唯一手段。**

## 4. 功能清单与优先级

### 4.1 MVP 需求清单（四列表）

`编号｜需求｜优先级｜相对基线`

**必填**：

- 编号排序与第 3 章一致。
- "相对基线"列写每条相对上一版基线的状态：`一致` / `一致（+团队共享）` / `新增（自 A4 拆分）` / `拆分（D-10）`。**这一列是文档可追溯性的关键**——读者一眼知道哪条是新的、为什么变。
- 表尾补一行**页面范围**（列出全部页面编号 + 总数）。
- 表后一段列**"某节点需求清单"**（如商业化节点的 H1b/T5b + 关联改动）。

### 4.2 阶段二（P1）

**一段话平铺**，每条一个短语，用分号分隔。**不列表格**。

### 4.3 阶段三（P2/P3）

同上，更短。

### 4.4 相对基线的调整说明（一致性审计）

**三列 `编号｜调整｜理由`**。

**必填**：每条理由回指决策编号（`决策 D-09`）或写清判断依据（`控制 MVP 体量`）。

**常见错误**：漏掉"因为某条决策带出的连锁调整"。**规则**：一条决策落地后，逐一检查它影响了哪些章节，在 4.4 里逐条列出。

## 5. 业务流程说明

### 5.x 每条流程

**形态**：`<pre><code>` 里的 ASCII 流程图 + 图后的规则说明。

**必填**：

- 流程图上**标页面编号**（`P01 首页`、`P02 Agent 模式`），让流程能落到界面。
- 图后**必须有一段规则/口径说明**（不是重复图的内容，而是图里放不下的约束）。
- 涉及状态的流程，**状态机要写全**（`草稿 → 排队 → 生成中 → 已完成/已失败 → 重试`），并逐状态写规则（哪些状态可取消、哪些失败不计量）。

**常见错误**：流程图漂亮但没有规则说明——图能看流程，看不出约束。

**必写的四类流程**（B 端产品）：

1. 核心主流程
2. **状态机**（长任务）
3. 多单元生产流程（批量 / 规模化）
4. 账号 / 组织生命周期
5. 计量或计费流程（含"当前生效"与"商业化后"两态）

## 6. 交互与页面说明

### 6.1 页面范围与跨文档对齐

**写**：页面清单以哪份文档为准 + MVP 交付几页 + **首版原型的优先顺序**（哪些页面因某决策提权）+ 跨文档滞后点清单（`1）…… 2）…… 3）……`）+ 冲突仲裁规则。

**常见错误**：不写原型优先顺序——设计师不知道先做哪页。

### 6.2 全局交互规则（G1、G2…）

**三列 `编号｜规则｜说明`**。

**必填的通用规则**（缺一条都是坑）：

| 规则 | 说明 |
|---|---|
| 异步任务全局可见 | 常驻入口 + 角标 + 浮层；**批量任务要展示聚合进度与"仅重试失败项"** |
| 用量 / 成本前置展示 | 提交按钮旁展示预估；完成后展示实际 |
| 错误反馈分级 | 参数错误行内提示 / 任务失败 Toast + 重试 / 服务异常全局横幅 + 降级说明 |
| 自动保存与版本 | 间隔与触发明写；版本历史可回滚 |
| 引用追溯 | 结果可回溯：引用了什么、什么参数、谁发起 |
| 消息通知矩阵 | **按场景逐条列"什么事件 → 什么通道 → 通知谁"**，并说明哪版是简版 |
| 新手引导 | 首登清单 + 空态模板 + 失败兜底文案；并回指它缓解哪个风险 |
| 帮助与支持入口 | FAQ / 工单 / 社群；经营侧 SLA 移交给就绪清单 |
| 合规摩擦最小化 | **合规动作集中到首次生成前一次性完成，不散落在各节点**；拦截页附原因 + 申诉入口 + 时效 |

**"合规摩擦最小化"这条极其重要也极容易被漏**：合规义务（实名、授权、标识）如果不配套体验设计，会变成用户流失的主要来源。

### 6.3 权限矩阵

**两层，两张表**：

- **组织级**：`操作｜角色A｜角色B`，用 `✓` / `✗` / `按项目角色`。
- **对象级**：`操作｜所有者｜编辑者｜查看者`。

表后用 `blockquote` 说明 MVP 的简化范围与后置项。

### 6.4 重点页面级规格

**用于基线未覆盖、由 PRD 补定义的页面**（不是替代原型稿）。

**形态**：`blockquote` 说明为何本节承担页面级定义 + ASCII 布局线框 + 六项规格列表：

`组件` / `状态`（正常 / 预警 / 达限 / 超限）/ `权限` / `跳转` / `验收标准` / `后续节点变化`

**常见错误**：把页面规格写成视觉稿描述。**它写的是信息架构与状态，不是配色与间距。**

---

## 7. 数据指标与埋点

### 7.1 指标体系

**形态**：ASCII 指标树。`北极星 → ├─ 维度 → │ ├─ 指标`。

**必填**：指标树末尾一段声明**目标值的来源**（"目标基线值在 MVP 上线后按首月数据校准，本版不预设"）。**不预设目标值，是专业度的体现，不是偷懒。**

**必带维度**：激活 / 留存 / 深度 / 变现准备（商业化前用"用量台账 + 影子账单"过渡，即"只算不收"）。

### 7.2 核心埋点事件表

**三列 `事件｜触发时机｜关键参数`**。

**必填**：事件名用 `snake_case`；参数要包含**能支撑指标计算的维度**（模式、来源、成员、用量、耗时、是否引用资产）。

**判据**：第 7.1 章的每个指标，能不能只用这张表里的事件算出来？不能就补事件。

### 7.3 数据口径定义

**两列 `口径｜定义`**。

**必填**：所有会被多章引用的关键口径。定义要写到**可计算的精度**：

> 成片 = 主动导出、时长 ≥30 秒、含 ≥1 条音频轨与字幕轨的 MP4

**常见错误**：口径写在正文里散落各处，没有集中定义 → 第 7 章和第 2 章的数字对不上。

---

## 8. 非功能需求

### 8.1 性能

**两列 `项｜基线`**。

**必填**：

- 基线数字**必须带来源或标注假设**。开头用 `blockquote` 声明："下表基线在 {某前置条件} 完成前为假设值，须以 {来源} 校准后冻结。"
- 区分**平台侧指标**（不受外部制约）与**外部依赖侧指标**（受供应商 SLA 制约）。

**常见错误**：写"响应要快""性能优良"。**每条都是数字 + 单位 + 前提。**

### 8.2 合规义务

**四列 `编号｜义务｜需求表述（EARS）｜状态`**。

开头加一句正文（不是标题括注）："下表各项均为上线前置条件，缺一项即阻塞对应里程碑，须逐条确认到责任人。"

**必填**：

- 义务逐条拆开（AI 生成内容标识 / 内容安全 / 声音克隆授权 / 上传素材版权 / 备案边界 / 实名与账号 / 上线资质）。
- **状态列必须写实**：`已入需求` / `需法务确认实现口径` / `待确认（附录 B-x）` / `未启动——周期可能长于开发周期`。
- 涉及资质办理的，写明**哪几项阻塞哪个里程碑**、哪些随商业化节点办理。

**这是全文最长的一张表之一。** 合规写不细，上线前必然返工。

### 8.3 安全与数据

**无序列表 3–5 条**：数据隔离 / 加密 / 权限回收时效 / 数据导出与删除。

### 8.4 兼容性

**短列表**：平台形态（Web / 桌面壳 / 移动端在不在范围内）+ 浏览器/系统基线 + 保留可能性的说明。

### 8.5 运维与可靠性

**两列 `项｜要求`**：降级矩阵（每类能力 ≥2 家供应商 + 切换阈值 + 切换要通知谁 + 要记审计）/ 监控告警（哪几类核心告警）/ 并发与配额 / 灰度与回滚。

### 8.6 数据保护

**两列 `项｜要求`**：备份（RPO / RTO 数值 + 恢复演练要求）/ 回收站（保留期 + 谁能彻底清除）/ 分层存储（长期 / 默认 / 归属 + 配额策略）。

## 9. 依赖与风险

### 9.1 外部依赖

**三列 `依赖｜内容｜影响`**。

**必填**：第三列写**它影响我们的什么**（哪个需求的实现载体 / 哪个成本模型输入 / 阻塞哪个里程碑）。

**常见错误**：只列依赖名字。**依赖表的产出是"影响"，不是清单。**

### 9.2 风险清单

**四列 `编号｜风险｜等级｜对策`**。

**必填**：

- 等级三档：`高` / `中` / `低`。
- **对策要落到具体机制**，且尽量回指章节（`多供应商冗余 + 适配层抽象 + 降级矩阵（8.5 节）`）。
- **至少一条风险要写"技术难度被低估"**这类内部风险——只写外部风险的风险表是不完整的。
- **风险 Top3 要与评审速览一致。**

**常见错误**：对策写"加强关注""持续跟进"。**没有机制的对策等于没写。**

---

## 10. 里程碑与验收

### 10.1 里程碑

`阶段｜内容｜准出条件`

**必填**：

- 准出条件**可检查**，且尽量回指章节与就绪清单条目。
- **不含日期**（写"排期需研发负责人评估确认"），或只写相对周期。
- **商业化节点独立**（`M-BC`），并带 Go/No-Go 量化门槛。
- **每个里程碑至少有一条"软指标"**（如"≥3 个种子客户完成全链路"）——纯硬指标的里程碑会漏掉"做出来了但没人用"。

### 10.2 验收冒烟清单

**有序列表**，10–15 条。**每条是端到端场景，以"——全程无阻断"收尾**。

**必含五类**：主流程 / 关键能力闭环 / 多角色链路 / 异常与冲突 / 合规拦截。

**常见错误**：写成功能点核对单（"导出功能可用"）。**冒烟测的是链路，不是功能。**

## 附录 A. 需求变更记录

**四列 `版本｜日期｜变更｜依据`**。

**必填**：每条变更写清"改了什么 + 依据是什么（决策编号 / 评审意见 / 用户决策）"。变更条目要**分点写**（`1）…… 2）…… 3）……`），一条变更可能带出十几处联动修改，全都要列。

**常见错误**：只写"文档优化"。**要写优化了什么。**

## 附录 B. 待确认问题清单

**四列 `编号｜问题｜建议责任方｜状态`**，开头用 `blockquote` 汇总全局状态（哪几条已关闭、哪几条阻塞哪个里程碑）。

**必填**：状态四档 —— `已确认：{结论}` / `阻塞 Mx` / `待确认` / `排期待定`。（**不写 ✅ / ⚠️ 这类 emoji**，粉标红态由模板脚本按状态词注入。）

**判据**：正文里所有"待确认""待评审确认""定级待确认"字样，都能在这张表里找到对应编号。**这是全文唯一的"未决事项总账"。**

## 附录 C. 参考文档索引

**两列 `文档｜用途`**（或三列含版本）。列出所有影响本文档的外部材料，并写明**它提供什么输入**。

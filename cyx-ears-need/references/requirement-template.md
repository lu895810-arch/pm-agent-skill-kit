# 需求条目模板与 EARS 速查（requirement-template）

本文件是「六段式需求」的可抄模板与判据。**P0 需求照抄，P1/P2 用压缩式。**

---

## 一、EARS 五类句式速查

| 类型 | 句式 | 用途 | 何时必用 |
|---|---|---|---|
| **Ubiquitous** | 系统应始终…… | 全局约束、不可协商的规则 | 每条需求至少 1 条（数据隔离、权限、合规底线） |
| **Event-driven** | 当……时，系统应…… | 主流程行为 | 每条需求至少 2 条（核心动作） |
| **Unwanted** | 如果……（异常），则系统应…… | 异常与故障处理 | **每条需求至少 1 条**（最常被漏） |
| **State-driven** | 在……（状态）期间，系统应…… | 状态内行为、长任务 | 有状态的需求必用 |
| **Optional** | 在提供……（功能）的情况下，系统应…… | 可选能力、分阶段特性 | 有阶段化 / 可配置能力时用 |

**写句式时的三个硬要求**：

1. **有触发条件**——"当用户提交 X 后"比"支持 X"强十倍。
2. **有系统行为**——动词是"系统应 {做具体动作}"，不是"系统应支持/优化/提升"。
3. **有可测结果**——带上数字、时限、或可判定的结果（"生成结构化列表""保留全部输入""不占用配额"）。

### 句式与反例对照

| ❌ 空需求 | ✅ EARS 写法 |
|---|---|
| 支持剧本导入 | 当用户在 P04 粘贴文本或上传文件并提交后，系统应在 120 秒内（10 万字以内）完成解析，生成结构化的实体列表。 |
| 解析过程要有进度 | 在解析进行期间，系统应展示进度并允许取消，取消后原文保留。 |
| 解析失败要有提示 | 如果解析失败或无法识别有效结构，则系统应保留全部输入、指明失败原因，且不占用团队用量配额。 |
| 解析结果可修改 | 系统应始终允许用户在确认入库前编辑解析结果（增删改实体、合并重复项）。 |
| 生成要快 | 系统应在提交后 30 秒内完成平台侧排队（不含外部服务耗时）。 |
| 支持批量重试 | 当批量任务部分失败时，系统应支持"仅重试失败项"，已完成项不受影响、不重复计入用量。 |
| 团队数据要隔离 | 系统应始终保证不同团队间的数据严格隔离；跨团队不可见。 |
| 出问题要能查 | 当成员执行关键操作时，系统应记录审计日志（操作者/时间/对象/动作/结果）。 |

## 二、P0 需求模板（六段式，照抄）

```html
<h4>{编号} {需求名}（P0，{来源标注}）</h4>
<ul>
  <li><strong>用户故事</strong>：作为 {Ux}，我希望 {动作}，以便 {收益}。</li>
  <li><strong>EARS</strong>：
    <ul>
      <li>{Event-driven：当……时，系统应……}。</li>
      <li>{State-driven：在……期间，系统应……}。</li>
      <li>{Unwanted：如果……，则系统应……}。</li>
      <li>{Ubiquitous：系统应始终……}。</li>
    </ul>
  </li>
  <li><strong>验收标准</strong>：{可量化场景，含数字}。</li>
  <li><strong>关联页面</strong>：{P0X → P0Y}。</li>
  <li><strong>边界与异常</strong>：{失败/超限/冲突/空态；不确定的写清"以谁的评审为准"}。</li>
</ul>
```

标题里的**来源标注**是必填的，四类写法：

| 情形 | 写法 |
|---|---|
| 相对基线一致 | 不写（默认一致） |
| 本版新增 | `P0，{版本号} 新增（D-xx）` |
| 自某条拆分 | `P0，{版本号} 自 {原编号} 拆分` |
| 降级 / 提级 | `P0，{版本号} 自 {原编号} 降级` |
| 定级待定 | `P0，定级待评审确认 {B-xx}` |

**为什么要在标题里带来源**：读者读到这一条时，需要立刻知道"它是新的还是老的、为什么会变"。把这段历史塞进"影响"列或正文里，都会被跳过。

## 三、P1 / P2 压缩式（一行）

```html
<h4>{编号} {需求名}（P1）</h4>
<ul>
  <li>{一句主条目：是什么 + 为什么后置 / 依赖什么前置}。</li>
</ul>
```

例：

> **S2 产能统计（P1）**
> 集级完成率、单集制作周期、瓶颈环节统计、按集用量归集报表（阶段二，随任务中心与数据看板建设）。

**判据**：一句说清"是什么 + 为什么现在不做"。**不要因为"顺手"就把 P1 展开成六段**——那会让 P0 的重点被稀释。

## 四、架构约束类需求模板

用于"不是功能，但今天必须设计对"的约束。

```html
<h4>{编号} {约束名}（架构约束）</h4>
<blockquote>本条为设计约束而非用户可见功能：确保未来 {某扩展} 时无需 {某代价}。</blockquote>
<ul>
  <li><strong>EARS（Ubiquitous，设计约束）</strong>：
    <ul>
      <li>系统应采用"……"的模型；……应抽象为"……"，本阶段仅启用……。</li>
      <li>系统的……不应将"……"硬编码为唯一容器（即使该能力本阶段不启用，抽象也须在设计模型中预留）。</li>
    </ul>
  </li>
  <li><strong>EARS（Optional，后续版本）</strong>：
    <ul>
      <li>在提供……的后续版本中，……应可……。</li>
    </ul>
  </li>
  <li><strong>验收标准（本版）</strong>：{设计评审通过的具体检查点}；无"……"的硬编码。</li>
  <li><strong>关联页面</strong>：无（架构层）。</li>
</ul>
```

**这类需求的价值**：它把"未来要扩展"从一句愿望，变成**评审准入条件里的一个检查项**。

## 五、优先级判定

### 三档定义

| 档 | 含义 | 展开程度 |
|---|---|---|
| **P0** | MVP 必须。删掉后"从输入到产出"的主链路走不通 | 六段写全 |
| **P1** | 阶段二。有它更好，没它闭环仍成立；或依赖前置能力先落地 | 一行 |
| **P2/P3** | 阶段三 / 观望 | 一行或仅入清单 |

### 判定四问（每条需求过一遍）

1. 删掉它，**主链路**还走得通吗？走得通 → 不是 P0。
2. 它是**能力**还是**保障**？保障类（用量、审计、隔离、合规）容易被当成"可以后做"，但它们的缺失会导致**上线不能通过**，通常也是 P0。
3. 它能不能**拆成"最小形态（P0）+ 完整形态（P1）"**？优先拆，不优先砍。
4. 它的成本是不是**取决于某个外部依赖**？是 → 该外部依赖要进"阻塞项"，并与它一起决定优先级。

### 拆分命名法

```
H1  用量与商业化
 ├─ H1a 用量透明（P0，成本保护）           ← 统计、预估、四维归集、配额联动
 └─ H1b 订阅 + 积分 + 支付渠道（M-BC）      ← 商业化节点交付

T5  团队用量
 ├─ T5a 用量统计与配额（P0，软限制）         ← 提醒为主，可配置拦截；不涉金额
 └─ T5b 席位套餐与积分账单（M-BC）

A4  分集
 ├─ A4a 手动分集与跨集资产继承（P0）         ← 最小闭环
 └─ A4b AI 自动分集（P1）
```

**命名规则**：原编号 + 后缀字母 `a` / `b`（不用 `1` / `2`，避免与序号混淆）；正文注明"自 X 拆分"。

**拆分的三个原则**：

1. **按"能否独立交付"拆**，不按"功能大小"拆。
2. **成本保护与商业变现要拆开**——它们的时点不同，混在一起会让商业化绑架产品节奏。
3. **拆分必须七处联动**：清单表 / 正文条目 / 流程 / 埋点 / 口径 / 冒烟清单 / 变更记录。

## 六、需求条目自查（逐条过）

- [ ] 标题含编号 + 需求名 + 优先级 + 来源标注
- [ ] 用户故事引用的画像（`Ux`）在 2.2 节 里存在
- [ ] EARS 4–6 条，且五类中至少用了三类
- [ ] **至少一条 Unwanted（异常）**
- [ ] 没有"支持 / 优化 / 提升 / 完善 / 赋能"式空动词
- [ ] 验收标准含数字或可判定结果，能被直接转成测试用例
- [ ] 关联页面指向的 `P0X` 在 6.1 节 页面清单里存在
- [ ] 边界与异常写了失败 / 超限 / 冲突 / 空态中的至少两类
- [ ] 编号在本域内连续，无空号
- [ ] 本条若为拆分产物，已在七处联动更新

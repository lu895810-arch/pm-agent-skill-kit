# EARS 需求章法（cyx-ears-need）

> 本 skill 原名 `cyx-product-all-requirements`（2026-09-23 改名）。旧稿与本机其它技能里出现的旧名，指向的都是这一套章法。

## Purpose（目的）

把「一个想法 / 一堆素材 / 一份旧稿」整理成**一份能开评审会、能派工、能验收、能升版的完整 PRD**。

这套章法来自一份真实的、连续迭代七版的短剧 AI 平台 PRD（V1.0→V1.6，含 25 条 P0 需求 + 1 条架构约束、14 个页面、10 条决策记录、20 条待确认项、13 条风险）。它跑通了三件事，也正是本 skill 要交付的三件事：

1. **让评审者 3 分钟能开会**——评审速览 + 审阅议题（每条挂责任人）。
2. **让研发能直接派工**——每条需求写到「什么条件下、系统做什么、怎么算通过」的颗粒度。
3. **让文档能活过第一版**——决策有台账、待定有状态、变更有着落，半年后的人还能看懂当初为什么这么定。

**行业无关**：能力域的字母（A/B/C…）在不同行业装的东西不同，但十章骨架与"六段式需求"的写法不变。行业适配映射见 `references/capability-domains.md`。

## When to use（何时触发）

**本 skill 是「点名才上」的重装工具，不做自动触发。** 判据只有一条：用户有没有显式要这套章法。

**触发**（必须出现显式指令）：

- 用户点名技能名：`cyx-ears-need`。
- 用户要「EARS 六段式」「用户故事 + EARS + 验收标准」这套需求条目写法。
- 用户要「十章 PRD」「评审速览 + 审阅议题」「按我那份 PRD 的写法来」「像这份重装 PRD 一样」。
- 用户手里有想法、会议记录、竞品截图、旧版方案、原型稿，**并明确要求收敛成一份工程级 PRD**（含量产派工粒度）。

**不触发**（这些走别的 skill，别硬上）：

- 用户只说「写 PRD」「梳理需求」「需求文档」「需求清单」「划 MVP 范围」「做个需求评审稿」，没点名本 skill → 走 `cyx-summary-need`（轻量需求 brief，单文件 HTML 九段骨架）。**默认选它，不选本 skill。**
- 只做市场调研、不涉需求定义 → 用 `cyx-research-report`。
- 只是问一个产品概念、不需要成文交付 → 直接答。
- 纯界面设计稿 / 视觉稿，不涉需求 → 另说。

**为什么设这道门槛**：这套十章章法重、要求高（每条 P0 六段式、七处联动、机检 10 组全过）。用户要的是「快出一份能看能讲的需求文档」时，硬拉这套章法会产出超规格文档、拖长交付。**拿不准的时候，先用 `cyx-summary-need` 问一句要不要升到十章版。**

## 一、十章骨架（结构即章法）

一份合格 PRD 的完整顺序。**章不能少，也不能乱序**——它们是一条从"为什么做"到"怎么验收"的推进链。

```
【审阅层】（不等同正文，评审者只看这一层）
  0. 顶栏       版本 / 状态 / 阻塞徽章 / 一行摘要
  0. 评审速览    核心定位 · 首发范围 · MVP 内核 · 体量 · 明确不做 · 商业模式 · 北极星 · 阻塞项 · 并行启动 · 风险 Top
  0. 审阅议题    编号 + 议题 + 责任人（每条都能在会上落到人）
  0. 文档信息表  文档名/版本/日期/定位基线/范围决策/状态/关联文档
────────────────────────────────────────────
  1. 背景           问题定义 · 市场论证摘要 · 竞争格局与差异化 · 名词术语表 · 决策记录
  2. 产品定位与目标  核心定位 · 用户与画像 · 首发场景策略 · 目标与度量 · 北极星 · 非目标
  3. 需求描述（EARS） 能力域分组，每条需求六段式
  4. 功能清单与优先级  P0 全表 · P1/P2 压缩 · 相对基线的调整说明
  5. 业务流程说明      每条流程一张流程图 + 规则
  6. 交互与页面说明    页面范围 · 全局交互规则 · 权限矩阵 · 重点页面级规格
  7. 数据指标与埋点    指标树 · 埋点事件表 · 数据口径定义
  8. 非功能需求        性能 · 合规 · 安全与数据 · 兼容性 · 运维可靠性 · 数据保护
  9. 依赖与风险        外部依赖 · 风险清单（等级 + 对策）
 10. 里程碑与验收      阶段门（内容 + 准出条件）· 验收冒烟清单
【台账层】
 附录 A 需求变更记录  版本 / 日期 / 变更 / 依据
 附录 B 待确认问题清单 编号 / 问题 / 责任人 / 状态
 附录 C 参考文档索引
```

**逐章写什么、必填什么、常见错误——见 `references/chapter-playbook.md`。写每一章前先翻对应小节。**

## 二、八条章法铁律

这八条是这份 PRD 与"普通需求文档"的分水岭。缺一条，文档就会在评审会上被打回。

### 1. 评审速览先行

文档开头必须有**评审速览**，十行以内交代完整：核心定位 / 首发范围 / MVP 内核 / MVP 体量 / 明确不做 / 商业模式 / 北极星 / 阻塞项 / 并行启动 / 风险 Top3。

评审者的时间只有十分钟。他不该从第 1 章开始读。

### 2. 审阅层与正文层分离

审阅要点（议题 + 责任人）放在正文之前，每条格式固定为：`编号｜议题｜建议责任人`。

议题必须是**能当场决策的**，不是"我们讨论一下 X"。例：`B-3 关闭：首批供应商清单与商务条款（≥2 家冗余）——研发+商务`。

### 3. 每条需求六段式（P0 全展开，P1/P2 一行带过）

这是整套章法的核心。P0 需求必须写全六段：

| 段 | 写什么 | 判据 |
|---|---|---|
| **用户故事** | 作为 {角色}，我希望 {动作}，以便 {收益} | 指向画像里真实存在的角色 |
| **EARS 描述** | 4–6 条，五类句式混用 | 有触发条件、有系统行为、有可测结果 |
| **验收标准** | 可量化 / 可测的场景 | 能被测试同学直接转成用例 |
| **关联页面** | P0X → P0Y | 能顺着文档走到界面 |
| **边界与异常** | 失败、超限、冲突、空态怎么处理 | 有 Unwanted 句式兜底 |
| **优先级** | P0 / P1 / P2 | 与第 4 章清单一致 |

P1/P2 需求**只给一行主条目**（说明是什么、为什么后置），细节评审后补。这不是偷懒，是**防文档膨胀**——把 100% 的精力放在 P0 上。

模板与 EARS 速查见 `references/requirement-template.md`。

### 4. 一切"待定"显式管理

两张表贯穿全文，是文档可追溯性的全部来源：

- **决策记录（D-xx）**：`编号｜决策项｜结论｜影响`。被后续决策覆盖的，在"影响"列写明（如"初版决策，后被 D-05 扩展"）——**不删旧决策**。
- **待确认清单（B-xx）**：`编号｜问题｜建议责任人｜状态`。状态三档：`阻塞 Mx` / `待确认` / `已确认（结论）`。

正文里凡出现"待评审确认""定级待确认"，必须回指 `B-xx` 或 `D-xx`。**不允许出现无编号的悬空待定。**

### 5. 表格最后列必须是判断，不是复述

市场、竞品、依赖这三类表格，最后一列固定为「**对本产品的含义 / 启示 / 影响**」。

| ❌ 复述 | ✅ 判断 |
|---|---|
| 竞品 X 有无限画布与工作流复用社区 | "创作过程可视化 + 经验复用"是平台飞轮；CLI 开放建议纳入阶段三 |
| 依赖：模型供应商 | 不自研模型；首批清单未定（B-3）；建议按"一致性 > 成本 > 延迟"选型并保持 ≥2 家冗余 |

事实是素材，判断才是需求文档的产出。**只堆事实的需求文档，评审会必然问"所以呢"。**

### 6. 三个"必须有"

- **每个目标必须有度量**：目标表固定三列 `维度｜目标｜度量`。写不出度量的，不是目标，是愿望。
- **每个风险必须有对策**：风险表固定四列 `编号｜风险｜等级｜对策`，对策要落到具体机制（多供应商冗余 / 降级矩阵 / 埋点监控），不是"加强关注"。
- **每条性能基线必须标来源**：假设值就写"假设值，须以实测校准后冻结"，不标来源的数字就是拍脑袋。

### 7. 编号体系全覆盖

任何一句「见 1.5 节」都能落到唯一位置。编号规则：

| 对象 | 格式 | 备注 |
|---|---|---|
| 需求 | `{域字母}{序号}`，如 `A1`、`B3`、`T7` | 拆分用后缀字母：`A4` → `A4a`（P0）/ `A4b`（P1），并注明"自 A4 拆分" |
| 能力域 | 单个大写字母 `A`–`Z` | 一域一主题，见 第 4 章 |
| 决策 | `D-01` | 两位零填充 |
| 待确认 | `B-1` | 与决策分开编号 |
| 全局交互规则 | `G1` | 跨页面规则 |
| 合规义务 | `N1` | 含义务 + EARS 表述 + 状态 |
| 风险 | `R1` | 含等级 + 对策 |
| 里程碑 | `M0` / `M1` / `M2` / `M-BC` | 功能演进与商业化节点解耦 |
| 页面 | `P01` | 两位零填充 |

**要求拆分（如 "H1 拆为 H1a/H1b"）时必须同时更新**：清单表、正文条目、流程、埋点、口径、冒烟清单、变更记录——七处联动，漏一处就自相矛盾。

### 8. "明确不做"要写正，范围外要显式移交

- **非目标逐条写理由**，并给出替代或预留路径。不写"暂不支持"，写"不做 X，因为 Y；扩展按 Z 预留，开放时无需数据迁移"。
- **范围外事项显式移交**：经营 / 合规 / 组织类事项若不属于产品 PRD，移交给对应文档（如《上线就绪清单》），但**在 PRD 里保留"产品侧接口需求"一行回指**。不留接口 = 上线时才发现没人管。

## 三、需求写法（去 AI 味的硬约束）

需求描述是 PRD 最容易被写成"AI 生成物"的地方。纪律如下：

**1. 用"系统应…"，不用"我们打算…"**

| ❌ | ✅ |
|---|---|
| 支持剧本导入 | 当用户提交文本或文件后，系统应在 120 秒内完成解析，生成结构化的人物、场景、道具列表 |
| 优化生成速度 | 系统应在提交后 30 秒内完成平台侧排队（不含模型侧耗时） |
| 提升协作体验 | 当成员编辑同一对象时，系统应展示占用提示（成员姓名），冲突覆盖后推送提示并保留版本历史 |

**判据**：删掉"支持 / 优化 / 提升 / 完善 / 赋能"这类动词，看剩下的句子还有没有信息量。没有，就是空需求。

**2. 每条需求有一组完整的 EARS 兜底**

主流程（Event-driven）+ 状态（State-driven）+ 异常（Unwanted）+ 全局约束（Ubiquitous）+ 后置（Optional）五类混用。

**最常见的漏项是 Unwanted**——异常路径不写，研发按正常路径实现，上线后全是故障工单。

**3. 数字要能闭合**

文档里出现的所有计数必须互相对得上：头部 KPI（P0 需求数 / 页面数 / 待确认数）↔ 清单表实际行数 ↔ 正文小节数 ↔ 附录条目数。

改一条需求，先想清楚它会不会影响这四个数。——**这是机检脚本 `scripts/check-prd.py` 的主要职责。**

**4. 不用元语言**

不写"本节将从三方面展开""综上所述""值得注意的是""该功能旨在为用户提供"。直接写事实与规则。

**5. 标题写实体名词，不写自我描述**

章节标题只回答"这一章是什么"，不回答"这一章怎么用"。带括注的自我说明、"一句话 X" 这类前缀，是文档塑料味最集中的地方。

| ❌ | ✅ |
|---|---|
| 评审速览（一页纸） | 评审速览 |
| 2.1 一句话定位 | 2.1 核心定位 |
| 2.6 非目标（本版明确不做） | 2.6 非目标 |
| 8.2 合规（评审必读） | 8.2 合规义务 |
| 7.2 埋点事件表（核心） | 7.2 核心埋点事件表 |
| 10.2 验收冒烟清单（核心路径） | 10.2 验收冒烟清单 |

**判据**：把括号里的字删掉，标题的信息量掉了没有？掉了 → 那是真标签，写进正文；没掉 → 是自我描述，删。

**例外**：方法名与编号标签留在括号里是允许的，它们是检索锚点而非自我描述——`（EARS）`、`（P1）`、`（P2/P3）`、`（架构约束）`、`（P0，V1.0 新增）`。

**6. 不写排版符号**

**只保留两类符号**，其余一律换中文：

| 保留 | 为什么 |
|---|---|
| `→` `↓` `←` `↑` | 流程方向，人人读得出来 |
| `≤` `≥` `×` | 数值边界与算式，精确 |
| `✓` `✗` | 权限矩阵格子小，这是唯一可行写法 |
| `─ │ ┌ ┐ └ ┘ ├ ┬` | 等宽框图的结构线 |
| `—` `·` `、` `（）` | 中文标点本身 |

**以下一律不写**：

| ❌ | ✅ |
|---|---|
| `见 §1.5 决策记录` | `见 1.5 节决策记录` |
| `3–6 条` | `3～6 条` |
| `①…②…③…` | `1）2）3）` |
| `◆ 审阅要点` | 装饰图形用 CSS 的 `width/height + background` 画 |
| `⚠️ 未启动` | `未启动——说明`，粉标由脚本注入 |
| `✅ 已确认：结论` | `已确认：结论`，行降透明度由脚本处理 |
| `※` | 删掉，或写"注：" |

**判据**：一个不懂排版的中文读者，能不能把这个符号直接读出来？读不出来就是噪音。**章节引用一律写「X.Y 节」，不写 §。**

这条不只是格式洁癖：`§` 这类机器标记会让整份文档读起来像从别的体系里抄来的，评审者会先注意到符号，而不是内容。

**7. 术语先定义后使用**

凡在需求里出现的自造概念（"三模式""主体""配额""成片"），必须在术语表里有定义；凡有阶段性边界的（"商业化后启用"），定义里必须写明时点。

## 四、通用能力域地图（行业无关）

需求正文按**能力域**分组，每域一个大写字母。这是行业无关的骨架，换行业只换每域装的内容。

| 域 | 主题 | 通用要回答的问题 |
|---|---|---|
| **A** | 输入与结构化 | 外部素材怎么进来？怎么变成系统可用的结构化数据？格式与容量边界？ |
| **B** | 资产与复用 | 哪些对象要被反复引用？一致性怎么锚定？跨范围（跨项目/跨集/跨批）怎么复用？ |
| **C** | 自动化与智能 | 系统能替用户做多少？中间态是否可编辑？失败了怎么降级到手动？ |
| **D** | 核心生产 | 核心能力（生成/计算/交易/生产）怎么执行？参数与规格？ |
| **E** | 编辑与后处理 | 产出物怎么细化调整？局部修改成本？ |
| **F** | 任务与系统 | 长任务怎么排队、可见、重试、取消？ |
| **G** | 生态与扩展 | 开放接口？第三方集成？多语言 / 多区域？ |
| **H** | 计量与商业化 | 用量怎么算？成本归集到谁？配额还是计费？何时启用？ |
| **Q** | 质检与风控 | 质量怎么校验？偏差怎么提示？拦截还是提示？ |
| **R** | 治理与合规 | 法规义务？数据安全？审计？数据保护与备份？ |
| **S** | 规模化管线 | 批量生产怎么编排？进度与产能怎么可视？断点怎么续作？ |
| **T** | 多用户与协作 | 账号模型？角色权限？分工审阅？多租户隔离？ |

**挑选原则**：数一遍你的产品**真正需要**的域——通常 5–9 个。域太多说明颗粒度太细，合并；域太少说明漏了横切能力（协作、计量、治理最常被漏）。

**跨行业的字母映射示例见 `references/capability-domains.md`。**

## 五、优先级与阶段门

### 优先级三档

| 档 | 含义 | 展开程度 |
|---|---|---|
| **P0** | MVP 必须，缺了闭环不成立 | 六段式写全 |
| **P1** | 阶段二，验证后做 | 一行主条目 |
| **P2/P3** | 阶段三 / 观望 | 一行主条目或仅列入清单 |

**范围收敛的判据**：一条需求删掉后，"从输入到产出"的主链路还走得通吗？走得通 → 不是 P0。

**排序纪律**：功能清单（第 4 章）按 P0 全表 → P1 压缩 → P2/P3 压缩 的整体顺序呈现，P0 内按域连续、P1/P2 各自连续，整体不得逆序；brief 版（cyx-summary-need）则要求每个模块内需求行 P0→P1→P2 单调降序。

**多业务形态的产品先定 MVP 核心域**：当产品同时挂多条业务线 / 多种交付形态（如一个生产引擎同时对外做 SaaS、企业定制、行业解决方案）时，先识别一个 MVP 核心域（通常是最轻、最自动化的那一款），其余业务线作为**并行域**或**独立模块**纳入需求文档并分层标优先级——不把它们都当 P0 写进主链路，否则 MVP 体量失控。判断方法：任一业务线删掉后，其余业务线的"从输入到产出"主链路还能成立吗？能 → 它不该是 P0。

**优先做拆分而非砍掉**（本 skill 的关键手法）：

- `H1 用量与商业化` → `H1a 用量透明（P0，成本保护）` + `H1b 订阅计费（商业化节点）`
- `T5 团队用量` → `T5a 用量统计与配额（P0）` + `T5b 席位套餐与账单（商业化节点）`
- `A4 分集` → `A4a 手动分集（P0，最小闭环）` + `A4b 自动分集（P1）`

好处：**需求没被砍，只是分期**，商业价值与成本保护解耦，商业化不再绑架产品节奏。

### 阶段门（里程碑表固定三列）

`阶段｜内容｜准出条件`

- **准出条件必须可检查**——"性能达标"要写清哪份基线；"证照齐备"要写清哪几项。
- **功能演进与商业化节点解耦**：功能走 M1/M2/M3，商业化另立 `M-BC`。
- **宁可不写日期**，写"排期需研发负责人评估确认"，也不要拍脑袋写死时间。
- **商业化节点要有 Go/No-Go 量化门槛**（如"公测 ≥8 周 + ≥5 个客户完成全链路 + 核心指标连续 3 周上行 + 3 个月内必须决策"），避免无限期免费或无限期拖延。

### 验收冒烟清单

写**端到端场景**，不写单元测试：

> 团队内新建项目 → 导入 10 万字剧本 → 蓝图+分集 → 建角色 → 生成分镜 → 批量生成 → 局部修改一处 → 配音 → 字幕 → 预览 → 导出——**全程无阻断**。

再加异常场景若干条（制造一次失败、制造一次冲突、触一次配额、走一次合规拦截）。

## 六、工作流（执行顺序）

### Phase 0 — 范围确认（先问，别猜）

缺信息就问，一次问清。**八问**：

1. 业务 / 行业与产品形态（Web / App / 硬件 / 纯服务 / 内部系统）
2. 客户形态（B / C / 双端）——**首发的单一形态是哪个**
3. 首发场景（**只做一个**，其余置灰收意向）
4. 核心问题：用户现在用什么替代？代价是什么？
5. 谁买单、怎么收钱（或明确"本版不商业化"）
6. 能力边界：自研 vs 接入第三方；数据从哪来
7. 硬约束：合规 / 资质 / 成本 / 团队规模 / 交付时点
8. 交付形态：只要 PRD，还是要配套原型规格 / 上线就绪清单

用户只有想法、什么都答不上来时，**先按行业常识给一版假设并显式标注"假设待确认"**，进入 Phase 1，不要卡住不动。

### Phase 1 — 定调（先写第 1、2 章）

顺序：问题定义 → 市场/竞品摘要 → 差异化定位 → 核心定位 → 用户画像 → 首发场景 → 目标与度量 → 北极星 → **非目标**。

**非目标要早写**。它是后面所有范围争论的仲裁依据。

### Phase 2 — 建能力域地图

按 第 4 章 挑域、给域起名（字母 + 主题），画一张"域 → 需求条目"的草表。这步决定文档骨架，先给用户过一眼再往下写。

### Phase 3 — 逐条写需求（工作量主体）

按域逐条写六段式。**每写完一域就自检一次**：编号连续？每条都有验收标准？每条都有至少一条 Unwanted？

### Phase 4 — 收口七件事

功能清单与优先级 → 流程 → 交互与权限 → 指标与埋点 → 非功能 → 依赖与风险 → 里程碑与验收。

### Phase 5 — 附录台账

变更记录 → 待确认清单（**从正文里把所有"待确认"抓出来汇总，一条不落**）→ 参考文档索引。

### Phase 6 — 出审阅层

回到开头写评审速览 + 审阅议题。**顺序上最后写，位置在最前**——只有写完全文，才知道该让评审者决策哪五件事。

### Phase 7 — 机检与交付

```bash
python {baseDir}/scripts/check-prd.py <prd.html 或 prd.md>
```

全过再交付。交付物按 `cyx-doc-separate` 命名与分区。

## 七、产物形态

### 主产物

**单文件暗色科技风 HTML**，起手式：

1. 复制 `assets/template.html`（已含全部 CSS 与 JS，改内容即可）。
2. 视觉与组件类遵循 `cyx-html-style`；本模板已内联其调色板（`--bg-deep:#04071a` / `--cyan:#00F5D4` / `--magenta:#FF2E97` / `--yellow:#FFE74C` / `--purple:#B14AED`）。
3. 模板自带的 JS 会做六件事，**不用手写**：
   - 阅读进度条
   - 从 `h2/h3` 自动生成左侧 TOC + 滚动高亮
   - 表格自动包 `.tblw` 横向滚动容器
   - **徽章自动转换**：单元格纯文本 `P0` / `P1` / `P2` / `高` / `中` / `低` / `M0` / `M-BC` 自动变徽章；`阻塞 M0` 变红态并给整行加洋红左边线；`已确认：…` 行自动降透明度；`未启动——说明` 只把状态词换成粉标、后文原样保留
   - `V1.x 新增 / 拆分 / 后移 / 扩展` 自动打"新增标记"
   - 装饰图形（审阅议题的方点、返回顶部箭头）全部用 CSS 画，**不用字符图形**；`#bar` / `nav#toc` / `#top` 任一缺失只跳过对应功能，不影响其余脚本

**关键：写正文时只写纯文本。**优先级写 `P0` / `高` / `M1`，状态写 `阻塞 M0` / `已确认：结论` / `未启动——说明`，**不要手写徽章 HTML，也不要写 emoji**。

## 十、技能自我进化机制

> **上游通用条款**：判定、留痕、回退的共性规则见 `cyx-skill-evolution`；本节是它在 PRD 场景的落地。

**技能不是一次写死的。** 用户每提一次修改意见，都要判定是否具有跨项目通用性——通用就回写本 skill，个案只改当期产物。

### 触发时机

- 用户针对已交付 PRD 提出任何修改意见（结构 / 措辞 / 编号 / 范围 / 版式）。
- **同一类意见反复出现**——最强信号，说明不是当期文档的问题，而是 skill 的默认写法错了，要改默认值。

### 三步判定

| 1）归类 | 2）判通用性 | 3）定落点 |
|---|---|---|
| 归到 A–F 六类 | 换一个行业、换一个产品仍成立 → 回写 skill；只对这一份成立 → 只改产物；模糊 → 按通用处理，写成"判据"而非"硬值" | 见下表 |

### 反馈类型 → 落点映射

| 代号 | 类别 | 典型反馈 | 落点 |
|---|---|---|---|
| A | 章节结构 | 「缺一章」「章的顺序不对」「这块该单独成章」 | 本文件 第 1 章 + `references/chapter-playbook.md` 对应章 |
| B | 需求写法 | 「这条需求太虚」「异常没写」「验收标准不可测」 | 本文件 第 3 章 + `references/requirement-template.md` |
| C | 编号与台账 | 「编号乱了」「待确认漏了」「决策没写影响」 | 本文件 第 2 章第 4 条、第 2 章第 7 条 + 自查清单 |
| D | 范围与优先级 | 「这个不该进 MVP」「该拆成两期」 | 本文件 第 5 章 + 清单章 |
| E | 判断质量 | 「只堆事实没结论」「风险对策太空」 | 本文件 第 2 章第 5 条、第 2 章第 6 条 |
| F | 视觉与呈现 | 「太像 AI 生成的」「徽章不对」「标题塑料味」「类似 § 这种符号都不要了」 | 本文件 第 3 章第 5 条、第 3 章第 6 条、第 7 章 + `assets/template.html` + `cyx-html-style` + `scripts/check-prd.py` 组 10 |
| G | 命名与触发 | 「技能改个名」「以后别自动触发这个 skill」「这个 skill 只在点名时用」 | 本文件 frontmatter（`name` / `display_name` / `description`）+ 第「When to use」节 + 全仓引用改名 |

**G 类落盘纪律（改名与降级触发时容易漏）**：改名不是只动 frontmatter，要一次改干净四类地方——1）本 skill 的 `name` / `display_name` / `description` 与正文标题；2）本 skill 内所有文件里的自我引用（`references/*.md`、`scripts/*.py`、`assets/*.html` 的注释与标题）；3）**其它 skill 的交叉引用**（`cyx-summary-need`、`cyx-original-need-md`、`cyx-original-need-html`、`cyx-skill-evolution` 等）；4）用户级与项目级记忆文件里的技能清单。降级为「点名才上」时，还要把 `description` 里原有的宽泛触发词**删掉**——留着就等于没降级，模型照样会自动加载。

反馈逐条落到 `references/feedback-log.md`（与 `cyx-research-report` 同一套留痕习惯）。

### 落盘纪律（三不写）

1. **不与已有规则重复**——同类规则已在，就就地强化或补一条机检，不新起一节。
2. **不写死具体数值**——写"判据 + 判定方法"，不写具体数字（数值只是当前默认，会再变）。
3. **不写无法机检的模糊直觉**——写不成判据或检查项的，不进 skill。

### 沉淀后必做

1. 同步更新第 8 章自查清单（**规则与自查两处都要写**，只写前者会在自查时漏掉）。
2. 能机检的，落成 `scripts/check-prd.py` 的检查项。
3. 在 `references/feedback-log.md` 追加一行：`日期 / 用户原话（节选）/ 类别 / 落点 / 处置`。
4. 跑一次 `python scripts/check-prd.py` 确认没跑坏。
5. 用一句话告诉用户：「这条我记进 skill 了，以后默认这么做。」——方便他当场纠正（「这条是一次性的，别记」）。

### 规则会过时：允许回退

用户若推翻某条已沉淀的规则，做三件事：1）改条目——**不是删掉，而是标注适用边界**（"仅当 ×× 时"）；2）检查有无其他规则与它冲突；3）告知用户已回退。

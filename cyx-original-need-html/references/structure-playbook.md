# 逐章写法详解（structure-playbook · HTML 版）

本文件是 `SKILL.md`「一、产出物骨架」的展开。**每写一章前翻对应小节**：这里只写「这章必须回答什么问题、渲染成什么组件、容易写错在哪」。

**与 md 版的边界**：内容手法（阶段怎么切、八要素判据、来源分级、主线归纳、缺口池判据）一律见 `cyx-original-need-md` 的 `references/structure-playbook.md`，本文件**不重写**，只在 HTML 落点上展开。

文中范例取自一份真实跑通的稿子（LumenFlow 短剧 AI 平台，五阶段），用 `例：` 标出。范例只作写法参考，阶段数、入口名、用户角色都要按手上的产品换。

---

## 第 1 章 · 演进路径与当前遗留问题

**这章是全篇结论页。** 评审者可能只读这一章就下判断，所以它得独立成立——不依赖后面任何一章。

四件东西，按顺序：

| 位置 | 写什么 | 判据 / 常见错误 |
|---|---|---|
| 第 1 段（`p`） | 能力从哪来 + 走了哪几轮，每轮一个短语，用 `→` 串 | 写成公司介绍、融资经历、团队规模；或只列轮次而无概括 |
| 第 2 段（`p`） | 贯穿全篇的那对矛盾 + 商业上要同时照顾的几类人 | 写成价值观口号；只写矛盾不写「几类人」——后者是后面「目标用户」列与主线的伏笔 |
| `.note.risk` | 全篇最大的遗留问题，一句，标「（分析推断）」 | 写成「仍需持续优化」这类无法验证的话；一条以上会失焦，只留最狠的那条 |
| 三列表 | `阶段｜做什么｜从哪进｜适合谁`——把总览表的「入口怎么选」抽出来 | 与第 3 章总览表重复贴一遍。这四列回答的是**「我该点哪个」**，总览表回答的是**「它怎么长出来的」**，两表视角不同 |

例（LumenFlow）：

> 五个入口（创作 / 剧集制作 / 出海转绘 / 新建空项目 / 新画布）能力差别很大，普通用户很难一眼判断该点哪一个。

**判据**：把第 1 章单独复制出来发给没读过全文的人，他能不能说出「这产品在纠结什么、最大的问题是什么」。说不出 → 重写。

## 第 2 章 · 演进背景

只有两块，都不长。

**能力底座**：材料里列的模型 / 数据 / 供应链组成，一句到两句。模型名用 `code` 包裹（`Seedream-5.0`），档位用顿号并列。

**阶段编号的含义**（`.note`）：**有偏差才写，没偏差整块删掉。**

- 先说结论：编号是功能逻辑演进顺序，不严格等于上线先后；
- 再给一条观察证据；
- 尚未上线的入口在这里声明「规划中」，不与已上线入口混排。

例：

> 下表中的阶段 1–5 是**功能逻辑演进顺序**（从单镜头 → 工程化），不严格等于各入口的实际上线先后。据当前界面观察：左侧「创作」工作台（阶段1 单镜头能力的当前形态）是在【出海转绘】（阶段3）之后补齐到左侧导航的；【新画布】（阶段5）则为最后规划、近期上线的入口。

**常见错误**：把这条声明写成一段方法论自述（「本文采用逻辑顺序编号的方式，以便读者……」）——读者要的是「哪个是后补的」，不是「你为什么这么编号」。

## 第 3 章 · 阶段演进（全篇主体）

### 3.1 总览表（6 列）

一行一阶段，表里短、详情长。

| 列 | 写什么 | 判据 / 常见错误 |
|---|---|---|
| 阶段 | `阶段N：{形态名}` | 形态名与正文 `<h3>` 标题**逐字一致**，否则读者要猜是不是同一阶段 |
| 产品形态 | 用户拿到手的是什么 | 写「支持 XX 功能」是功能不是形态 |
| 核心入口 | 入口名（多个都列） | 与界面实际文案一致 |
| 解决痛点 | 用户当时最难受的处境 | 写用户处境，不写「提升效率」 |
| 目标用户 | **角色名** | 反例：「创作者」「企业用户」。正例：「编剧、小白创作者」「AI 动画师、短剧制作人、抽卡师」 |
| 遗留问题 | 天花板 + **点名**催生哪个阶段 | 列名带「遗留问题」就够，不必写「催生下一阶段」；正文里必须点到阶段号 |

**单元格超过两行就该下放。** 机制、参数、上限、按钮文案全部移进阶段小节。源稿踩过这个坑：阶段 2 的「遗留问题」格塞了近 200 字，整张表的扫读节奏被那一个格子打断——这类内容属于「局限」块，不属于总览表。

### 3.2 阶段小节

`<h3 id="s3-N">阶段N：{形态名}【{入口名}】</h3>`。形态名与总览表逐字一致，入口名加 `【】` 便于眼跳。

下面是块。**必写四块全阶段同构，块名与顺序不许飘**：

```
<h4>背景</h4>                    ← 上一阶段的遗留问题怎么催生本阶段；谁在提（句末标来源）
<h4>用户需求</h4><ul>…</ul>       ← 动词开头，写人想干什么
<h4>当前入口形态（界面观察）</h4>   ← 入口位置、流程、参数档位、按钮与提示原文、上限
<div class="note warn">局限：…</div> ← 天花板 + 点名催生阶段 N+1
```

**按需块**（材料里有才写，但同名块在别的阶段也用同一个名字）：`官方口径` / `定位` / `界面要素` / `实现功能` / `业务流程`。

**八要素落点**（md 版八要素在 HTML 里不许消失）：

| md 版八要素 | HTML 落点 |
|---|---|
| 背景与原始需求 | `背景` 块 |
| 用户需求 | `用户需求` 块 |
| 实现功能 | `官方口径` / `定位` / `实现功能` 块（按材料挑一个） |
| 当前入口形态 | `当前入口形态` + `界面要素` 块 |
| 满足与痛点 | 接在 `当前入口形态` 之后的一条 `.note.warn` |
| 产品局限 | `局限` 块（`.note.warn`） |
| 用户反馈 | 阶段尾注 `p.src`，前缀「用户反馈：」 |
| 业务侧视角 | 阶段尾注 `p.src`，前缀「业务侧视角：」 |

**块名漂移是这份稿子最常见的退化。** 源稿里阶段 1 用「用户需求」、阶段 2 用「用户诉求」，读者读到阶段 2 会以为换了件事——实际是同一块。定块名时一次定死，全篇照抄。

**「当前入口形态」是最容易写空、也最能看出有没有下过功夫的一块。** 要写到：入口位置、操作顺序、参数档位、按钮与提示原文（照抄界面）、上限与不可逆约束、状态与反馈。没有界面材料时写「待补观察」，不要凭材料想象界面。

**「局限」块必须点名。** 写法：{天花板是什么，为什么它在本阶段框架内过不去} → 催生阶段N+1 的 {形态名}。

**判据**：把这阶段的「局限」与下一阶段的「背景」并排读。读起来像「上一句说缺什么，下一句说于是要做什么」→ 过；像两件不相干的事 → 回去改，或承认这两阶段是并列关系而非演进关系。

**尾注只放两类内容**：用户反馈、业务侧视角。没有真实用户原话就**不编**——整条删掉，别把分析判断包装成用户口吻。

## 第 4 章 · 入口架构

演进讲完，把**当前**的入口按落位重排一遍。这一步的价值在于：演进顺序与「用户该点哪个」的顺序不是一回事，读者真正需要的是后者。

| 列 | 写什么 |
|---|---|
| 层级 | 从最轻到最重命名，用「能力档」的说法（快速测试 / 快速粗片 / 出海分发 / 自主创作 / 精细制作） |
| 能力 | `【{入口}】{一句话能力}` |
| 当前入口位置 | 左侧导航 / 首页 Tab / 我的项目卡片 |
| 备注 | 上线时机，或与相邻入口的关系 |

表后必须点出**最大遗留体验问题**（`.note.risk`）。这一句不是客套——它通常就是缺口池第一条的来源。

**常见错误**：把这张表按演进顺序排。排错了，它就成了第 3 章总览表的复制品，白写一章。

## 第 5 章 · 核心需求主线

主线是**贯穿两个以上阶段的拉扯**，不是阶段特征的复述。写 2–4 条。

**判据**：这条主线能不能解释两个以上阶段的取舍？只能解释一个的，那是阶段特征，不是主线。

每条主线一小节，内部三段推进：

1. **两端各自的做法**——自动模式怎么做、手动模式怎么做；或早期怎么做、现在怎么做；
2. **各自的代价**——上手简单但算力浪费 / 可控但劳动密集；用完即丢但省事 / 可复用但要维护；
3. **落到哪些功能上 + 一句行业判断**——如「精细改，不必推倒重来」。

第一类主线（两端对照）用四列表 + 一段话；第二类（单侧趋势）用两三段 + 一条 `.note` 收判断。**不必强求各主线长得一样**——它们的形状本来就不同，硬凑成同一张表反而失真。

**覆盖面自检**：几条主线最好分别落在「交互」「技术资产」「商业」三个面上。三面都覆盖，读者才会觉得这份稿子把产品看完了；三条都在讲交互，说明另外两个面没提炼出来。

## 第 6 章 · 需求缺口

三列：`缺口｜问题描述｜建议方向`，编号 `G1…Gn` 连续。

章首一句话 `p.dim` 交代范围（「以下缺口为后续迭代候选，优先级待产品确认」），**不写免责声明**——「未经第三方核验」「建议向厂商索取书面确认」这类是写给审阅者的过程交代，不进文档。

**与阶段「局限」严格区分**——这是最容易混的一处：

| | 阶段局限 | 需求缺口 |
|---|---|---|
| 时间轴 | 历史，已被下一阶段解决 | 现在，还没解 |
| 位置 | 阶段小节的 `局限` 块 | 第 6 章的缺口池 |
| 作用 | 解释下一阶段为什么存在 | 变成下一版的需求池 |

落笔前过一遍：这条是不是已经被某个后续阶段解决了？是 → 它属于阶段局限，不进缺口池。

**缺口的来源通常有三处**，找不齐时按这三处扫一遍：① 第 1 章与第 4 章点出的最大遗留问题；② 各阶段「暴露痛点」里至今仍在的；③ 材料里写了、界面里没有的（承诺与实现的差额）。

## 第 7 章 · 用户旅程流转

`pre` 里把阶段串成一条链，一阶段一行，缩进两层：

```
新用户进入
  → 先用【创作】做单镜头测试（需求：快速验证人设动作）
  → 验证可行，尝试【剧集制作】一键成片（需求：快速拿到完整剧集粗片）
```

**这一章是给读者做验收用的**：顺着链走一遍，中间若有一处「为什么从这里跳到那里」说不通，说明前文的链子有断点。它同时是下游 PRD 用户故事的直接素材。

**与前三张表的分工**：总览表按阶段横排，入口架构按当前落位横排，用户旅程按**时间顺序纵向**走一遍——三个视角都写了，读者才既看得到结构、又看得到路径。

---

## 第 8 章 · 口径与来源

三列表：`类型｜含义｜本文使用方式`，覆盖三级标签（产品官方口径 / 界面观察 / 分析推断）。作用只有一个——告诉读者**哪句能直接引用、哪句只能参考**。

**这一章到此为止。** 不写「整理说明」「本稿以 XX 为原稿做叙事结构与表格化整理」「如需与现有需求文档合并，建议将第 3 章作为产品背景插入」——那是交接备忘，属于交付说明，不属于文档本身。也**不写**免责类话（「未经第三方核验」「正式引用前建议向厂商索取书面确认」）：口径归属靠标签本身表达，标签后面不必再补「可信度如何」。

## 九、返工最多的六个原因（交付前逐条自查）

1. **阶段切错**：把「同一个入口加了个按钮」当新阶段，或把两件事塞进一个阶段。回 `cyx-original-need-md` 第三节三条判据重切。
2. **链子断**：某阶段的遗留问题，下一阶段没接住；或下一阶段的背景凭空出现。把总览表最后一列与每阶段第一段并排读一遍，能抓出来。
3. **总览表被塞满**：格子写成小作文，机制与参数该下放的下放。源稿的实例是阶段 2 的「遗留问题」格。
4. **块名漂移**：同一块在不同阶段叫不同名字（「用户需求」/「用户诉求」）。定块名时一次定死。
5. **无来源的产品事实**：价格、上限、客户名没标来源。逐条挂标签，挂不上的降为待确认。
6. **加工痕迹进正文**：口径声明、免责语、修订流水、「本文档怎么整理出来的」写在正文或第 8 章里。全删——口径图例留表，其余归交付说明。

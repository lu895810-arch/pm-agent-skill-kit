# 单产品功能演进与需求分析（HTML 交付版 · cyx-original-need-html）

## Purpose（目的）

把「一个产品今天长这样，是怎么一步步走到今天的、每一版在解什么需求」讲清楚，交出一份**评审者打开就能看、能直接投影讲、能锚点引用**的单文件 HTML。

它来自一份真实跑通的稿子（LumenFlow 短剧 AI 平台：五阶段 + 五层入口 + 三条主线 + 六个缺口），那份稿子做对的三件事就是本 skill 的交付标准：

1. **一条链**——每个阶段的遗留问题直接催生下一个阶段。把总览表最后一列与下一阶段第一段并排读，能对上。
2. **扫读友好**——左侧目录常驻、章节带编号块、表格先给全局、详情下放到阶段小节。评审者不读正文也能在 3 分钟内对完演进路径与遗留问题。
3. **能接着用**——缺口池直接变成下一版需求池，阶段「用户需求」直接派生出 PRD 用户故事，界面要素直接变成验收要点。

**单产品边界（硬约束）**：一次只分析一个产品。要横向比多家（可灵 / 海螺 / Pika 这类）→ 走 `cyx-research-report`。

---

## When to use（何时触发）

**触发**：

- 用户要梳理某产品的「功能演进 / 需求演进 / 迭代路径 / 几个入口是什么关系」，要一份**能直接点开看**的 HTML。
- 用户手里有白皮书、业务介绍、官网、教程、官方模板、界面截图、用户反馈，要串成一条演进链。
- 用户要从「现在的产品」反推「当初的原始需求」，作为写需求文档 / PRD 的输入。
- 用户说「像 LumenFlow 那份功能演进与需求分析那样出一份」。

**不触发**：

- 要 Markdown 主文档、后续要接 PRD 与多格式链路 → `cyx-original-need-md`（本 skill 的上游同源技能）。
- 直接写 PRD / 需求文档 → `cyx-ears-need`；轻量需求 brief（单文件 HTML）→ `cyx-summary-need`。
- 多厂商横向对比、市场份额、商业模式盘点 → `cyx-research-report`。
- 只罗列功能清单、不追演进与需求成因 → `cyx-summary-need`。

**与既有 cyx 技能的分工（不重复造）**：

| 事项 | 归谁 |
|---|---|
| **阶段切法、八要素判据、来源分级、主线归纳、缺口池判据** | `cyx-original-need-md`（内容手法唯一出处，本 skill 不重写） |
| **HTML 八章骨架、左侧目录、组件类、表格列、渲染规则、机检** | **本 skill** |
| 暗色科技风视觉规范（配色语义、反塑料味、去 emoji、标题语言） | `cyx-html-style` |
| 语言总纲（通俗 / 严谨 / 逻辑闭环 / 衔接 / 去 AI 味） | `~/.workbuddy/MEMORY.md`「语言总纲」 |
| 数据可信红线、多格式同源链路 | `cyx-research-report` |
| 素材分区、文件命名、成品归档 | `cyx-doc-separate` |
| 下一步的需求文档 / PRD | `cyx-summary-need` / `cyx-ears-need` |

## 一、产出物骨架（八章，顺序不可乱）

```
左栏目录（常驻，带章号）+ 头部（产品名 / 一句话导语 / 六格指标 / 状态徽章）
────────────────────────────────────────────
1. 演进路径与当前遗留问题   全篇结论页：能力来自什么 + 一直在解哪对矛盾 + 最大遗留问题 + 「N 个入口怎么选」对照表
2. 演进背景                 能力底座（模型 / 数据 / 供应链）+ 阶段编号口径声明
3. N 阶段演进总览           总览表（一行一阶段）→ 逐阶段小节（每阶段四块同构 + 按需块）
4. N 层入口架构             按**当前落位**重排的入口表 + 最大遗留体验问题
5. N 条核心需求主线         贯穿两阶段以上的拉扯，每条一小节
6. 现存需求缺口             后续迭代需求池，编号 G1…Gn
7. 用户旅程流转             从新用户到精品生产的递进链（ASCII）
8. 口径与来源               三类事实标签的图例（产品官方口径 / 界面观察 / 分析推断）
```

**为什么比 md 版多两章。** md 版把结论与背景压在导语三块、把口径声明放头部一句；HTML 是网页阅读——评审者从目录点进来，可能直接落在任何一章，所以结论单独成第 1 章、口径单独成第 8 章，两章都能被目录与外部链接直接锚定。

**逐章写什么、常见错误 → `references/structure-playbook.md`（每写一章前先翻对应小节）。**
**起手骨架 → `assets/template.html`（复制后替换占位符，占位符写成 `{产品名}` 这类可被机检抓到的形式）。**

## 二、唯一事实源（同源链路）

HTML 是**渲染层**，不是第二份内容。

| 手上有什么 | 怎么开工 |
|---|---|
| 只有原始材料（白皮书 / 官网 / 截图 / 反馈） | 按 `cyx-original-need-md` 的手法在稿上把内容立起来，再按本 skill 骨架落成 HTML |
| 已有 md 版演进稿 | 内容以那份 md 为事实源，**只做骨架重排与渲染**；HTML 里不得出现与 md 冲突的事实 |
| 已有 HTML，要改内容 | 先改源稿（md 或素材归集），再重新渲染；**不直接手改 HTML 正文**——手改一处，源稿与 HTML 就开始分叉 |

判据：任意一条事实被质疑时，能指向源稿的哪一句或哪份材料。指不出来 → 不进正文。

## 三、结构：总览表与入口架构表

**（1）阶段总览表（6 列，一行一阶段）**

`阶段｜产品形态｜核心入口｜解决痛点｜目标用户｜遗留问题`

- 「目标用户」写到**角色名**（源稿写「AI 动画师、短剧制作人、抽卡师」，不写「创作者」）。
- 「遗留问题」列的每一条都要在正文里被下一阶段接住。
- **表里短、详情长**：单元格超过两行，就该把机制、参数、上限下放到阶段小节。源稿踩过这个坑——阶段 2 的「遗留问题」格塞了近 200 字，整张表的扫读节奏被它打断。

**（2）入口架构表（4 列，按当前落位排序）**

`层级｜能力｜当前入口位置｜备注`

层级从最轻到最重排（快速测试 → 快速粗片 → 分发 → 自主创作 → 精细制作），**不是按演进顺序**。表后必须点出最大遗留体验问题，用 `.note.risk` 写一句——这一句通常就是缺口池第一条的来源。

**（3）缺口池（3 列，编号 G1…Gn 连续）**

`缺口｜问题描述｜建议方向`

**与阶段「局限」严格区分**：局限是历史（已被下一阶段解决），缺口是现在（还没解）。已解决的局限不得进缺口池。

## 四、阶段小节：四块同构 + 按需块

每个阶段是一段 `<h3 id="s3-N">`，下面是若干 `<h4>` 块。**块名与块顺序在同构的四块上必须完全一致**——读者读阶段 4 时会自动拿它和阶段 3 对齐，块名一飘他就得重新找。

**必写四块（全阶段同构）**：

| 块 | 落在哪个标签 | 必须回答 |
|---|---|---|
| `背景` | `<h4>` + `<p>` | 上一阶段的遗留问题怎么催生本阶段；**谁**在提这个要求（句末标来源） |
| `用户需求` | `<h4>` + `<ul>` | 动词开头，写人想干什么，不写功能名 |
| `当前入口形态（界面观察）` | `<h4>` + `<p>` / `<ul>` | 入口在哪、点进去什么流程、参数档位、按钮与提示原文、上限与不可逆约束 |
| `局限` | `.note.warn` | 天花板在哪，并**点名**催生阶段 N+1；不点名的局限等于没写 |

**按需块（材料里有才写，但同名块的块名全篇统一）**：

| 块 | 什么时候写 |
|---|---|
| `官方口径` / `定位` | 该阶段有白皮书、官网或教程的正式表述 |
| `界面要素` | 界面细节多到要单独列表（参数、按钮、状态、序号） |
| `实现功能` | 需要先说清「产品做出来的是什么」再谈界面 |
| `业务流程` | 该阶段是一条可画出来的多步流程 |

**md 版八要素在 HTML 里不许消失**，只是换了落点：

| md 版八要素 | HTML 落点 |
|---|---|
| 背景与原始需求 | `背景` 块 |
| 用户需求 | `用户需求` 块 |
| 实现功能 | `官方口径` / `定位` / `实现功能` 块（按材料挑一个） |
| 当前入口形态 | `当前入口形态` + `界面要素` 块 |
| 满足与痛点 | 接在 `当前入口形态` 后面的一条 `.note.warn` |
| 产品局限 | `局限` 块（`.note.warn`），点名下一阶段 |
| 用户反馈 | 阶段尾注 `p.src`，前缀「用户反馈：」 |
| 业务侧视角 | 阶段尾注 `p.src`，前缀「业务侧视角：」 |

**阶段编号纪律**：编号是**功能逻辑演进顺序**，不严格等于上线先后。有偏差时在第 2 章显式声明，并在总览表或入口架构表里点出实际落位。

**链式闭环检验**：每写完一个阶段，把它的「局限」与下一阶段的「背景」并排读——读起来像「上一句说缺什么，下一句说于是要做什么」→ 过；像两件不相干的事 → 回去改，或承认这两阶段是并列关系而非演进关系。

## 五、视觉与组件

**视觉定位：扁平暗色，不是霓虹玻璃。** 本模板沿用「深灰底 + 单色青绿主色 + 细线分隔」的文档质感——它比 `cyx-html-style` 的深空蓝霓虹风**更平、更静**，因为这份稿子是给人逐条读与逐条改的，不是数据看板。差异是有意的，不是漏了样式：不铺径向光晕、不铺网格背景、不加玻璃质感。

**组件速查（模板已内联全部 CSS 与 JS，无需外链）**：

| 用途 | 类 / 结构 |
|---|---|
| 左侧常驻目录 | `nav#toc` + `h3` + `a`（二级用 `a.l2`）；滚动时当前项自动高亮（`.on`） |
| 顶部信息区 | `header` > `.brand`（产品名 · 品类）/ `h1` / `.kick`（一句话导语）/ `.metas`（六格指标）/ `.hd-r`（状态徽章） |
| 指标格 | `.meta` > `.k`（小写出处标签）+ `.v`（值） |
| 状态徽章 | `.bdg` + `.b-v`（青，结构类）/ `.b-w`（琥珀，口径类）/ `.b-b`（蓝，来源类） |
| 章标题块 | `.part-banner` > `.pnum`（编号方块）+ `h2` + `.pdesc`（一句话说明本章答什么） |
| 小节标题 | `h3`（青绿左竖线）；块标题 `h4` |
| 表格 | 外层 `.tblw`（窄屏横向滚动）+ `table`（表头深底） |
| 说明注 | `.note`（青，机制/口径）/ `.note.warn`（琥珀，局限/痛点）/ `.note.risk`（红，最大遗留问题） |
| 阶段尾注 | `p.src`（小灰字，用户反馈 / 业务侧视角） |
| 弱化引言 | `p.dim`（章首交代范围的一句话） |
| 行内术语与代码 | `code`（模型名、参数值、按钮原文） |
| 流程链 | `pre`（用户旅程、业务流程） |
| 双栏 | `.two-col`（两组并列信息） |
| 返回顶部 | `#top`（滚动超 400px 出现） |

**组件纪律（继承 `cyx-html-style` 并落到本模板）**：

1. 一个章节不超过两种组件类；`.note` 三种色按语义用，不叠色。
2. `.pnum` 只用在章标题块，不滥用；页内不再重复页码。
3. 高饱和色只作点缀：一章里青绿（主）+ 琥珀或红（强调）合计不超过两处。
4. 表格不炫技，靠留白与细线区分；列宽随内容自适应，不做彩色斑马纹之外的装饰。
5. 版式三层收敛：`.part-banner`（章）→ `h3`（阶段/条目）→ `h4`（块）；需要更细就改列表或表格，不继续造标题层级。

## 六、三类事实标签（HTML 的渲染方式）

同一份稿子里的「事实」不等重。动笔前先给每条事实归级，落笔时按下面这套渲染：

| 级别 | 来源 | 怎么标（HTML 写法） |
|---|---|---|
| 一级 · 产品官方口径 | 白皮书、业务介绍、官网、教程 / 知识库公告、官方模板 | 句末写 `（白皮书口径）`、`（业务介绍披露）`；同一材料内部口径冲突，分开列出 |
| 二级 · 界面观察 | 产品实际界面截图 / 试用 | 块标题或段末写 `（界面观察）`；只主张「当前实现」，不主张「官方承诺」 |
| 三级 · 分析推断 | 由事实推导的产品逻辑、用户痛点、迭代方向 | 段首写 `（分析推断）`，且必须能指回它依据的那条事实；无依据的推断不进正文 |
| 四级 · 用户反馈 / 口述 | 用户原话、需求方口头说明 | 阶段尾注 `p.src` 前缀「用户反馈：」；涉及价格、对外承诺、合规的一律降为待确认 |

**三类标签的图例必须收在第 8 章**（模板已给表）——它是读者判断「哪句能引用、哪句只能参考」的唯一依据。

**界面观察与材料口径不是替代关系**：截图看到的是「现在怎么做」，材料写的是「承诺怎么做」。冲突时两条都留——材料口径进正文并标来源，界面观察作为核对线索写进同一段。

判据：这条事实若被质疑，我指向哪份材料、哪张截图、哪句原话？指不出来 → 不进正文，降为待确认。

## 七、语言与视角纪律

结构之外，写法遵循全局 cyx 设定（`cyx-html-style`「一、语言风格规范」「四、AI 塑料味反面案例」+ `~/.workbuddy/MEMORY.md`「语言总纲」）。本节只落**本稿特有的硬约束**：

1. **叙述主体是「产品 / 界面 / 用户」，不是「我们」**。正文不写「我们 / 我方 / 本次调研」，也不拿文档当主语（不写「本文档把……归成五类」）。讲产品行为用产品名或入口名作主语，讲诉求用用户角色作主语。
2. **每处事实带来源标签**。至少做到每阶段一处材料口径、全篇至少一处界面观察；不出现无来源的产品事实（价格、参数、上限、客户名）。
3. **不写修订流水与加工痕迹**。不写「整理说明」「本稿以 XX 为原稿做整理」「如需与现有需求文档合并，建议……」——那是交接备忘，放交付说明，不进文档。版本与状态放头部信息区。
4. **术语首次出现给白话定义**，写「是什么 ＋ 为什么叫这个名」。源稿的范例是给「Harness」补「（行业里指把模型能力包成产品的那层应用）」——换个同义词不算解释。
5. **不用图标当标签**。`✅` / `⚠️` 一律换成加粗文字标签（`满足需求` / `暴露痛点`）或 `.note` 组件；正文不出现 emoji。链条用 `→`，并列用 `＋`，分隔用 `｜`（这些是标点，保留）。
6. **材料口径冲突不硬凑统一**。同一件事（模型名、价格、单位）在不同材料里说法不一致时，分别列出、标明各出自哪份材料；不猜一个「看起来对」的值填进去。
7. **`p.src` 尾注只承载「用户反馈 / 业务侧视角」两类内容**，不放免责声明、口径声明、审阅建议。
8. **`.brand` 写产品名与品类**（如「LUMENFLOW · AI 短剧创作平台」），不写「XX 风格」「整理自 XX」这类描述本文格式的元信息。

## 八、执行流程

### Phase 0 — 收料与定边界（先问，别猜）

一次问清五件事：

1. 分析对象是哪个产品——**只一个**。公司有多条业务线时先定是哪一条，其余在第 2 章作背景一句带过。
2. 材料清单：白皮书 / 业务介绍 / 官网 / 教程 / 模板 / 截图 / 用户反馈，各有哪些。
3. 有没有界面观察（截图或可试用的产品）。没有就把「界面要素」块写成「待补观察」，并说明本稿只到材料层面。
4. 阶段里是否包含**尚未上线**的入口——含的话必须在第 2 章声明「规划中」，不能与已上线入口混在一张表里不加区分。
5. 交付形态：只要 HTML，还是同时要 md 版（要的话先出 md，再按第二节同源链路渲染）。

用户答不上来时，先按常识给一版假设并显式标「假设待确认」，继续往下走，不卡住。

### Phase 1 — 切阶段，先给用户过一眼

按 `cyx-original-need-md` 第三节三条判据切完，列一版「阶段编号 → 一句话形态 → 入口」草表，**确认后再展开**。这一步返工最便宜。

### Phase 2 — 复制模板，填头部与第 1、2 章

```bash
cp {baseDir}/assets/template.html <你的产出路径>.html
```

先定下六格指标（版本 / 内容基线 / 整理日期 / 演进阶段数 / 入口层级数 / 核心需求主线数）与状态徽章，再写第 1 章结论页与第 2 章背景。这几处定了，全篇基调就定了。

**目录与正文同步增删**：阶段小节加一个，目录的 `a.l2` 就加一个；章不加，目录链接也不留。

### Phase 3 — 填总览表，再逐阶段展开

总览表 6 列一次填满（「遗留问题」列先写关键词，正文会反复引用它），然后按顺序写阶段小节。每写完一个阶段做三件事：①「局限」是否点名了下一阶段；②下一阶段的「背景」能否接上；③本阶段有无无来源的产品事实。

### Phase 4 — 入口架构 + 需求主线

入口架构按**当前落位**重排一遍（顺序与演进顺序不同）；主线从阶段表里横向提取，每条要能解释两个以上阶段的取舍。

### Phase 5 — 缺口池 + 用户旅程 + 口径图例

缺口池每条指回具体材料或界面现象；用户旅程用 `pre` 把阶段串成一条链，一阶段一行；第 8 章填三类标签图例。与阶段局限重叠的、已解决的，从缺口池删掉。

### Phase 6 — 机检与交付

```bash
python {baseDir}/scripts/check_original_need_html.py <产出文件>.html
```

退出码 0（允许 WARN）＝ 可交付；1 ＝ 有 FAIL，按输出逐条修。再过第九节自查清单，最后按 `cyx-doc-separate` 命名与归档。

**交付前手工过一遍**：浏览器打开，点一遍目录每个链接（锚点都要跳得到）、滚到中段看目录高亮跟不跟、窄屏拉一下看宽表能不能横向滚。

**骨架**
- [ ] 八章齐全、顺序正确；目录项与章一一对应，无空链接

- [ ] 头部六格指标齐全；「演进阶段 / 入口层级 / 主线」三格数字与正文实际计数一致

- [ ] 除末阶段外，每阶段都有「局限」块且**点名**了催生哪个阶段
- [ ] 除首阶段外，每阶段的「背景」都接住了上一阶段的遗留问题

## 十、机检脚本

```bash
python {baseDir}/scripts/check_original_need_html.py <产出文件>.html
```

退出码 0（允许 WARN）＝ 可交付；1 ＝ 有 FAIL。检查项：

| 组 | 检查内容 |
|---|---|
| 1 | 八章骨架齐全、顺序正确（按 `h2` 关键词序） |
| 2 | `.part-banner` 数量 ＝ `<section>` 数量；`.pnum` 编号 1…8 连续 |
| 3 | 总览表 6 列且含「目标用户」「遗留问题」列 |
| 4 | **阶段数闭合**：总览表数据行数 ＝ `<h3 id="s3-N">` 小节数，编号连续 |
| 5 | **链式闭环**：除末阶段外每阶段有 `.note.warn` 局限块并点名阶段 N+1 |
| 6 | 来源标签密度：每阶段 ≥1 处；全篇「界面观察」或「待补观察」至少一处 |
| 7 | 缺口池 `G1…Gn` 编号连续、无重号 |
| 8 | 去 AI 味：emoji / 图标标签 / 空话词 / 元语言 / 正文出现「我们」「我方」「本次调研」/ 加工痕迹词 |
| 9 | 占位符残留（`TODO` / `待填` / `{产品名}` 这类花括号占位） |
| 10 | 目录锚点全部可达；单文件自包含（无外链 CSS / JS） |

**Windows 编码坑（务必先设）**：PowerShell 捕获 Python 输出默认走 GBK，脚本 print `→`、`≤` 会抛 `UnicodeEncodeError`，表现为「输出为空」，容易误判成脚本挂了。先设 `$env:PYTHONIOENCODING = "utf-8"` 再跑。

## 十二、自我进化机制（遵循 cyx-skill-evolution 通用条款）

> **上游通用条款**：判定、留痕、回退的共性规则见 `cyx-skill-evolution`；本节是它在演进稿 HTML 交付场景的落地。

**本技能不是一次写死的。** 用户对 HTML 稿提的每一条修改意见，都可能是适用于所有后续同类稿子的规则；通用项回写本文件或 `assets/template.html`，个案只改当期产物。

### 12.1 触发时机

- 用户对**骨架 / 目录 / 表格列 / 组件 / 配色 / 版式**提意见（「少一章」「目录该常驻」「这个格子太长」「配色太亮」）。
- **同一类意见反复出现（≥2 次）**——最强信号：不是当期稿子的问题，而是本 skill 的默认写法错了，要从「建议」升为强约束。
- 我自己发现本 skill 有错命令、缺步骤、过时写法——不等指令，当场修。

### 12.2 落点映射

| 反馈类型 | 典型原话 | 改哪里 |
|---|---|---|
| 骨架与顺序 | 「缺一章」「顺序不对」「这章该独立」 | 一 + `references/structure-playbook.md` 对应章 |
| 目录与锚点 | 「目录不跟着滚」「链接点不到」 | `assets/template.html` 的 `nav#toc` 与 JS + 一 |
| 表格列 | 「列太多」「少一列 X」 | 三 + `assets/template.html` 表头 + 脚本组 3 / 4 |
| 阶段块与链 | 「这个阶段少了背景」「没说催生谁」 | 四 + `references/structure-playbook.md` 第三节 + 脚本组 5 |
| 来源与口径 | 「这个数哪来的」「别硬凑统一」 | 六 + `references/feedback-log.md` |
| 视觉与组件 | 「配色太亮」「组件太重」 | 五 + `assets/template.html` 的 CSS；视觉通则转 `cyx-html-style` |
| 语言与措辞 | 「太像 AI 写的」「看不懂」 | 七 + `cyx-html-style` 一；能机检的落进脚本组 8 |
| 内容手法（阶段怎么切、八要素） | 「这两个阶段该合并」 | **转 `cyx-original-need-md`**（内容手法不在本 skill 维护） |

### 12.3 落盘纪律（三不写）

1. **不与已有条目重复**——同类已在，就地强化表述或补一条机检，不新起一节。
2. **不写死具体数值与个案结论**——写「判据 ＋ 判定方法」，不写具体章数 / 列数 / 颜色值（那是当前默认，会再变，也不适用于别的产品）。
3. **写不成判据的模糊直觉不进文件**——要么落成对照表一行，要么落成自查清单一项或脚本检查项。

### 12.4 沉淀后必做

1. **规则与自查两处同步**：改了正文条款，必须同步第九节自查清单，否则下次交付仍会漏。
2. **能机检的落成脚本检查项**：硬规则加进 `scripts/check_original_need_html.py` 并跑一遍。
3. **回扫四处落点**：本文件正文、`references/structure-playbook.md`、`assets/template.html`（表头与骨架）、自查清单——改一处核其余三处。
4. 在 `references/feedback-log.md` 追加一行：`日期 / 原话节选 / 类别 / 归属 skill / 落点 / 处置`。
5. 跑一次脚本确认没改坏；用一句话告知用户「这条我记进 cyx-original-need-html 了，以后默认这样做」，方便他当场纠正。

### 12.5 规则也会过时：允许回退

用户推翻某条 → ① 改对应条目并**标注适用边界**，不直接删除；② 在 feedback-log 追加「规则回退」；③ 查有无其他条目与之冲突（尤其「一、骨架」与「四、阶段四块」之间、「五、视觉」与 `cyx-html-style` 之间）。

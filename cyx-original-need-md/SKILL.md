# 单产品功能演进与需求分析（cyx-original-need-md）

## Purpose（目的）

把一个产品「今天长这样，是怎么一步步走到今天的」讲清楚，并且**每一版都说得出来它当初在解什么需求**。

产出物是一份 Markdown《{产品} 功能演进与需求分析》。它来自一份真实跑通的稿子（LumenFlow 短剧 AI 平台：五个阶段 + 五层入口 + 三条主线 + 六个缺口），那份稿子做对的三件事，就是本 skill 的交付标准：

1. **一条链**——每个阶段的遗留问题直接催生下一个阶段。把总览表最后一列和下一阶段第一段并排读，能对上。
2. **每阶段八要素**——背景 → 用户需求 → 实现功能 → 当前入口形态 → 满足与痛点 → 局限 → 用户反馈 → 业务侧视角，缺一块就说不清「为什么会有这个功能」。
3. **能接着用**——缺口池直接变成下一版需求池，演进链直接派生出 PRD 用户故事与埋点指标。

**单产品边界（硬约束）**：一次只分析一个产品。要横向比多家（可灵 / 海螺 / Pika 这类）→ 走 `cyx-research-report`。

---

## When to use（何时触发）

**触发**：

- 用户要梳理某产品的「功能演进 / 需求演进 / 迭代路径 / 几个入口是什么关系」，要一份能直接打开看的 Markdown。
- 用户手里有白皮书、业务介绍、官网、教程、官方模板、界面截图、用户反馈，要串成一条演进链。
- 用户要从「现在的产品」反推「当初的原始需求」，作为写需求文档 / PRD 的输入。
- 用户说「帮我看看这产品是怎么长成这样的」「这几个功能为什么并存」。

**不触发**：

- 直接写 PRD / 需求文档 → `cyx-ears-need`；轻量需求 brief（单文件 HTML）→ `cyx-summary-need`。
- 多厂商横向对比、市场份额、商业模式盘点 → `cyx-research-report`。
- 只罗列功能清单、不追演进与需求成因 → `cyx-summary-need`。

**与既有 cyx 技能的分工（不重复造）**：

| 事项 | 归谁 |
|---|---|
| 章节骨架、阶段切法、八要素、主线归纳、缺口池、机检 | **本 skill** |
| Markdown 标题层级、表格、加粗、措辞、论证与口径写法 | `cyx-md-style` |
| 语言总纲（通俗 / 严谨 / 逻辑闭环 / 衔接 / 去 AI 味） | `~/.workbuddy/MEMORY.md`「语言总纲」 |
| **HTML 交付版**（八章骨架、左侧目录、组件类、渲染机检） | `cyx-original-need-html`（内容同源：以本 skill 的稿子为事实源，只做骨架重排与渲染） |
| 视觉通则（配色语义、反塑料味、去 emoji、标题语言） | `cyx-html-style` |
| 数据可信红线、多格式同源链路 | `cyx-research-report` |
| 素材分区、文件命名、成品归档 | `cyx-doc-separate` |

## 一、产出物骨架（六段 + 一个可选）

```
# {产品} 功能演进与需求分析（结合 {材料清单}）

> 导语三块（各占一段，不分小节）
>   ① 能力底座与演进路径：靠什么能力，走了哪几轮，每轮一句话
>   ② 始终在解的核心矛盾：贯穿全篇的张力 + 商业上要同时照顾的几类人
>   ③ 编号口径声明：阶段编号是功能逻辑顺序，不严格等于上线先后（有偏差必须写，没偏差整块删掉）
────────────────────────────────────────────
## 演进阶段总览
      8 列：阶段｜产品形态｜核心入口｜实际入口上线现状｜解决核心痛点｜目标用户｜关键需求｜遗留问题（催生下一阶段）
## 分阶段拆解：每阶段产品形态、用户诉求、功能点、迭代驱动力
      ### 阶段1：{形态名}（【{入口名}】）—— 八要素，每阶段同构
      ### 阶段2 …
## {N} 层入口架构（按当前落位）
      4 列：层级｜能力｜当前入口位置｜备注 ＋ 一段最大遗留体验问题
## 产品演进背后的 {N} 条核心需求主线
      ### 主线1：{两端对仗的矛盾}
## 现存需求缺口（后续迭代需求池）
      编号 G-n：缺口｜现状证据｜影响
## 用户旅程视角的需求流转
      代码块递进链，一阶段一行
────────────────────────────────────────────
## 可进一步产出方向（可选）
```

**段不能少、不能乱序**——它是一条从「这产品是什么」推到「下一步做什么」的链。

- 逐段写什么、常见错误 → `references/structure-playbook.md`（每写一段前先翻对应小节）
- 起手骨架 → `assets/template.md`（复制后填，占位符写成 `{...}`）

## 二、四类来源分级与标注（动笔前先归级）

正文里每一处事实都要能回答「你凭什么这么说」。四类来源，进的章节不同，标注方式也不同：

| 级别 | 来源 | 能支撑什么 | 怎么标 |
|---|---|---|---|
| 一级 · 原始材料 | 白皮书、业务介绍、官网、教程 / 知识库公告、官方模板 | 全部章节：定位、能力、模型与参数、计费、目标客户 | 句末或段末标来源（`（白皮书口径）`、`（业务介绍披露）`）；同一材料内部口径冲突，分开列出 |
| 二级 · 界面观察 | 产品实际界面截图 / 试用 | 入口形态、页面流程、按钮文案、参数档位与上限 | 段首或段末写「（据产品界面观察）」；只主张「当前实现」，不主张「官方承诺」 |
| 三级 · 用户反馈 / 口述 | 用户原话、需求方口头说明 | 用户诉求、痛点、阶段驱动力 | 引述块写原话并标「（用户反馈）」；涉及价格、对外承诺、合规的**一律降为待确认** |
| 四级 · 衍生归纳稿 | 已经二次归纳过的演进分析、现状梳理、缺口清单 | 只支撑演进背景 / 入口架构 / 需求主线 / 缺口池 | 不得作为产品事实（价格、能力、参数）的来源，引用时写明用途仅限演进与缺口 |

**判据**：这条事实若被质疑，我指向哪份材料、哪张截图、哪句原话？指不出来 → 不进正文，降级为待确认。

**界面观察与材料口径不是替代关系**：截图看到的是「现在怎么做」，材料写的是「承诺怎么做」。冲突时两条都留——材料口径进正文并标来源，界面观察作为核对线索写进对应段落（源稿的做法：把「界面显示单价 × 时长 = 扣费积分」写进待确认项的核对线索里，而不是拿它去覆盖材料口径）。

## 三、阶段怎么切（本 skill 的核心手法）

**切一个阶段的判据**：出现新的产品形态或新入口，且它打破了上一个形态的某个天花板。三条同时成立才算一阶段：

1. 有新的入口 / 新模式（不是同一入口加了个按钮）；
2. 有新的目标用户或新的诉求（**说不出来是谁在提 → 不成立**）；
3. 上一个阶段有明确的天花板被它打破（**说不出来破了什么 → 不成立**）。

**编号纪律**：

- 阶段编号是**功能逻辑演进顺序**（从最原始的能力到工程化），不严格等于上线先后。凡两者有偏差，**必须在导语第 ③ 块显式声明**，并在总览表单列「实际入口上线现状」一列。源稿正是如此：左侧「创作」工作台是在「出海转绘」之后才补进导航的，但逻辑上它属于阶段 1。
- 一个阶段盖两件事必须拆；两个阶段的诉求与痛点若完全相同必须合并。

**链式闭环检验（每写完一段抽一次）**：把总览表某行的「遗留问题」列与下一阶段正文的「背景与原始需求」并排读——问题在不在？在，链子接上了；不在，要么补，要么承认这两阶段是并列关系而非演进关系（那就得改总览表的排法）。

## 四、分阶段八要素（每阶段同构）

每阶段固定八块，用加粗小标题起段（**不升成 `####`**），让一个阶段一眼扫完：

| 块 | 写什么 | 判据 |
|---|---|---|
| **背景与原始需求** | 上一阶段跑通后，谁提出了什么新要求 | 承接上一阶段的「遗留问题」，开头一句把因果接上 |
| **用户需求** | 编号 `1. 2. 3.`，动词开头，写人想干什么 | 每条能对应一个真实角色；出现功能名说明写的是功能不是需求 |
| **实现功能** | 产品做出来的是什么，落在哪个入口 | 一句说清入口、一句说清机制 |
| **当前入口形态** | 入口在哪、点进去什么流程、参数档位、按钮文案、上限 | 标「（据产品界面观察）」；有具体数值（比例、时长、消耗、上限）就写上 |
| **满足与痛点** | 满足什么 ＋ 暴露什么 | 用加粗文字标签起行（`**满足需求**` / `**暴露痛点**`），**不用图标** |
| **产品局限（驱动下一阶段）** | 天花板在哪，并点名催生阶段 N | **必须点名**；不点名的局限等于没写 |
| **用户反馈** | 一段用户原话，引述块 | 是用户的口吻，不是分析者的判断 |
| **业务侧视角** | 这个入口在商业上承担什么 | 指向具体客户类型或产能指标，不写「提升竞争力」 |

完整的阶段写作骨架（含范例）见 `references/structure-playbook.md` 第二节。

## 五、三张表怎么列

**（1）演进阶段总览（8 列，一行一阶段）**

表里短、详情长。「关键需求」列写需求侧要点（用 `→` 串流程），不写功能清单；「目标用户」列**写到角色名**（源稿写的是「AI 动画师、短剧制作人、抽卡师」，不是「创作者」）；「遗留问题」列的每一条都要在正文里被下一阶段接住。

**（2）N 层入口架构（4 列）**

`层级｜能力｜当前入口位置｜备注`。层级按**当前落位**从最轻到最重排（快速测试 → 快速粗片 → 分发 → 自主创作 → 精细制作），不是按演进顺序。表后必须点出**最大遗留体验问题**（源稿：「5 个入口能力差异大，普通用户难以快速判断该点哪个入口」）。

**（3）需求缺口池（`G-n` 连续编号）**

`编号｜缺口｜现状证据｜影响`。

**与「阶段局限」严格区分——这是本 skill 最容易混的一处：**

| | 阶段局限 | 需求缺口 |
|---|---|---|
| 时间轴 | 历史——已被下一阶段解决 | 现在——还没解 |
| 位置 | 阶段小节内的「产品局限」块 | 独立章节的缺口池 |
| 作用 | 解释下一阶段为什么存在 | 变成下一版的需求池 |

已解决的局限不能进缺口池；缺口池每条都要有现状证据（哪份材料、哪个界面现象说明它还没解），说不出来就是判断不是缺口。

## 六、需求主线怎么归纳

主线是**贯穿两个以上阶段的拉扯**，不是阶段特征的复述。写 2–4 条。

**判据**：这条主线能不能解释两个以上阶段的取舍？只能解释一个的，那是阶段特征，不是主线。

写法 `### 主线N：{两端对仗的矛盾}`，内部三段推进：

1. 矛盾两端各自的做法（自动模式怎么做、手动模式怎么做）；
2. 各自的代价（上手简单但算力浪费 / 可控但劳动密集）；
3. 落到哪些功能上，收一句行业判断。

源稿三条可作范式：`可控性 VS 自动化的持续权衡`、`资产沉淀（从临时生成到可复用数字内容资产）`、`用户群体扩张（个人玩家 → 专业创作者 → B 端商业团队）`。三条恰好覆盖「交互」「技术资产」「商业」三个面——挑主线时可以照这个覆盖面自检。

## 七、语言与视角纪律

结构之外，写法遵循全局 cyx 设定（`cyx-md-style`「三、语言规范」「四、逻辑与口径」+ `~/.workbuddy/MEMORY.md`「语言总纲」）。本节只落本 skill 特有的硬约束：

1. **叙述主体是「产品 / 界面 / 用户」，不是「我们」**。正文不写「我们 / 我方 / 本次调研」，也不拿文档当主语（不写「本文档把……归成五类」）。讲产品行为用产品名或入口名作主语，讲诉求用用户角色作主语。
2. **每处事实带来源标签**。至少做到每阶段一处材料口径、全篇至少一处界面观察；不出现无来源的产品事实（价格、参数、上限、客户名）。
3. **不写修订流水与元叙述**。不写「本文将从三方面展开」「综上所述」「值得注意的是」；版本与文档状态放头部，不进正文。
4. **术语首次出现给白话定义**，写「是什么 ＋ 为什么叫这个名」。源稿的范例是给「Harness」补「（行业里指把模型能力包成产品的那层应用）」——这类解释要能让人用自己的话复述，换个同义词不算解释。
5. **不用图标当标签**。`✅ 满足需求` / `⚠️ 暴露痛点` 一律换成加粗文字标签 `**满足需求**` / `**暴露痛点**`；正文不出现 emoji。链条用 `→`，并列用 `＋`，分隔用 `｜`（`→` 是标点，保留）。
6. **材料口径冲突不硬凑统一**。同一件事（模型名、价格、单位）在不同材料里说法不一致时，分别列出、标明各出自哪份材料，并挂待确认；不猜一个「看起来对」的值填进去。
7. **单位与命名与源材料一致**。混用（积分 / 秒与元 / 秒并存、兑换比缺失）要点出来，不自行换算。

## 八、执行流程

### Phase 0 — 收料与定边界（先问，别猜）

一次问清五件事：

1. 分析对象是哪个产品——**只一个**。公司若有多条业务线，先定是哪一条，其余在导语里作背景一句带过；
2. 材料清单：白皮书 / 业务介绍 / 官网 / 教程 / 模板 / 截图 / 用户反馈，各有哪些；
3. 有没有界面观察（截图或可试用的产品）。没有就说明本稿只写到材料层面，「实际入口上线现状」列填「待补观察」；
4. 阶段里是否包含**尚未上线**的入口——含的话必须在导语声明「规划中」，不能与已上线混在一张表里不加区分；
5. 交付形态：只要 Markdown，还是后续要 HTML 版 / 直接进 PRD。

用户答不上来时，先按常识给一版假设并显式标「假设待确认」，继续往下走，不卡住。

### Phase 1 — 切阶段，先给用户过一眼

按第三节三条判据切完，列一版「阶段编号 → 一句话形态 → 入口」草表，**确认后再展开**。这一步返工最便宜。

### Phase 2 — 写总览表

8 列一次填满。「遗留问题」列先写关键词，后面正文会反复引用它。

### Phase 3 — 逐阶段展开八要素

按顺序写。每写完一个阶段做三件事：①「产品局限」是否点名了下一阶段；②下一阶段的「背景与原始需求」能否接上；③本阶段有无无来源的产品事实。

### Phase 4 — 入口架构 + 需求主线

入口架构按**当前落位**重排一遍（顺序与演进顺序不同）；主线从阶段表里横向提取。

### Phase 5 — 缺口池 + 用户旅程

缺口池每条指回具体材料或界面现象；用户旅程用代码块把阶段串成一条链，一阶段一行。与阶段局限重叠的、已解决的，从缺口池删掉。

### Phase 6 — 自检与交付

```bash
python {baseDir}/scripts/check_original_need_md.py <产出文件>.md
```

再过第九节自查清单；交付物按 `cyx-doc-separate` 命名与分区。

## 九、交付前自查清单

**骨架**
- [ ] 六段齐全、顺序正确（总览 → 分阶段拆解 → 入口架构 → 需求主线 → 缺口池 → 用户旅程）；可选「可进一步产出方向」写了才留
- [ ] 导语三块在位：能力底座 / 核心矛盾 / 编号口径声明（无偏差时第③块已删）
- [ ] 未上线的入口已显式标「规划中」，未与已上线入口混排

**阶段与链**
- [ ] 总览表 8 列齐全，一行一阶段
- [ ] 阶段编号连续无跳号；总览表行数 ＝ 正文阶段小节数
- [ ] 每个（除末阶段）都有「产品局限」块，且**点名**了催生哪个阶段
- [ ] 每个（除首阶段）的「背景与原始需求」都接住了上一阶段的遗留问题
- [ ] 每阶段八要素齐全，无缺块；各阶段同构（块名一致、顺序一致）
- [ ] 「用户需求」条目是动词开头的诉求，不是功能名
- [ ] 「目标用户」写到角色名，不是「创作者 / 用户」这类泛称

**表与台账**
- [ ] 入口架构表 4 列，按当前落位排序；表后点出最大遗留体验问题
- [ ] 缺口池编号 `G-n` 连续；每条有现状证据 + 影响
- [ ] 缺口池里没有「已被下一阶段解决」的条目（那是阶段局限，不是缺口）
- [ ] 需求主线 2–4 条，每条能解释两个以上阶段；不是阶段特征的复述

**来源与口径**
- [ ] 每阶段至少一处来源标签；全篇至少一处「（据产品界面观察）」
- [ ] 无无来源的产品事实（价格、参数、上限、客户名）
- [ ] 材料之间口径冲突处未硬凑统一，已分别标注来源
- [ ] 衍生归纳稿未被当作产品事实来源

**语言**
- [ ] 正文无「我们 / 我方 / 本次调研」；无「本文档把……归成……」这类拿文档当主语
- [ ] 无 emoji、无图标当标签（`✅` / `⚠️` 已换成加粗文字标签）
- [ ] 无「赋能 / 抓手 / 闭环 / 颗粒度」空话；无「综上所述」「值得注意的是」「首先 / 其次 / 最后」三段套
- [ ] 术语首次出现有白话定义（不拿同义词当解释）
- [ ] 标题是实体名词，无「一句话 X」「核心要点」这类空标签

**机检**
- [ ] `python scripts/check_original_need_md.py <文件>` 退出码 0

## 十、机检脚本

```bash
python {baseDir}/scripts/check_original_need_md.py <产出文件>.md
```

退出码 0（允许 WARN）＝ 可交付；1 ＝ 有 FAIL，按输出逐条修。检查项：

| 组 | 检查内容 |
|---|---|
| 1 | 六段骨架齐全、顺序正确 |
| 2 | 总览表 8 列，且含「目标用户」「遗留问题」列 |
| 3 | **阶段数闭合**：总览表行数 ＝ 正文 `### 阶段N` 小节数，且编号连续 |
| 4 | **链式闭环**：每行遗留问题非空；除末阶段外每阶段有「产品局限」块并点名下一阶段；「用户需求」块名全篇一致（不出现部分阶段写「用户诉求」） |
| 5 | 来源标签密度（每阶段至少一处）与类别覆盖（材料 / 界面观察） |
| 6 | 缺口池 `G-n` 编号连续，未与模块式 `G1` 混用 |
| 7 | 去 AI 味：emoji / 图标标签 / 空话词 / 元语言 / 正文出现「我们 / 我方 / 本次调研」 |
| 8 | 占位符残留（`TODO` / `待填` / `{...}`） |
| 9 | 编号引用可命中（正文引用的「阶段N」不超出实际阶段数） |
| 10 | 入口架构表 4 列、导语三块在位 |

**Windows 编码坑（务必先设）**：PowerShell 捕获 Python 输出默认走 GBK，脚本 print `→`、`≤` 会抛 `UnicodeEncodeError`，表现为「输出为空」，容易误判成脚本挂了。先设 `$env:PYTHONIOENCODING = "utf-8"` 再跑。

**脚本基线（2026-09-23 实测）**：拿本 skill 的源稿 `LumenFlow功能演进与需求分析.md` 跑，结果是 2 FAIL / 7 WARN——FAIL 落在「阶段 4 正文没写产品局限块（只在总览表里提了）」和「正文用了 `✅` `⚠️` 图标当标签」两处；WARN 集中在「总览表部分行的遗留问题没点名下一阶段」「缺口池用的是 `1. 2. 3.` 而非 `G-n`、且不是四列表」。这三处是源稿真实存在的体例偏差，不是脚本误报——若哪天要把那份稿子再发一版，按这三条顺一遍即可。合规样例（本次同时验证）可达 FAIL 0 / WARN 0，退出码 0。

## 十二、自我进化机制（遵循 cyx-skill-evolution 通用条款）

> **上游通用条款**：判定、留痕、回退的共性规则见 `cyx-skill-evolution`；本节是它在演进与需求分析场景的落地。

**本技能不是一次写死的。** 用户对演进稿提的每一条修改意见，都可能适用于所有后续同类稿子；通用项回写本文件，个案只改当期产物。

### 12.1 触发时机

- 用户对**骨架 / 阶段划分 / 表格列 / 来源标注 / 语言**提意见（「少一段」「阶段切得不对」「这两列合并」「来源标清楚」）。
- **同一类意见反复出现（≥2 次）**——最强信号：不是当期稿子的问题，而是本 skill 的默认写法错了，要从「建议」升为强约束。
- 我自己发现本 skill 有错命令、缺步骤、过时写法——不等指令，当场修。

### 12.2 落点映射

| 反馈类型 | 典型原话 | 改本文件哪一节 |
|---|---|---|
| 骨架与顺序 | 「缺一段」「顺序不对」「这个该单独成章」 | 一 + `references/structure-playbook.md` 对应段 |
| 阶段划分 | 「这两个阶段该合并」「这个不该算一阶段」 | 三（判据）+ `references/structure-playbook.md` 第二节 |
| 表格列 | 「列太多」「少一列 X」「顺序反了」 | 五 + `assets/template.md` 的表头 + `scripts/check_original_need_md.py` 组 2 / 10 |
| 来源与口径 | 「这个数哪来的」「两边说法不一样，别硬凑」 | 二 + 七（第 2、6 条） |
| 语言与措辞 | 「太像 AI 写的」「看不懂」「不要图标」 | 七 + `cyx-md-style`；能机检的落进脚本组 7 |
| 下游衔接 | 「顺便把需求文档也写了」 | 十一（转出去，不在本 skill 里做） |

### 12.3 落盘纪律（三不写）

1. **不与已有条目重复**——同类已在，就地强化表述或补一条机检，不新起一节。
2. **不写死具体数值与个案结论**——写「判据 ＋ 判定方法」，不写具体阶段数 / 列数（那是当前默认，会再变，也不适用于别的产品）。
3. **写不成判据的模糊直觉不进文件**——要么落成表格里的对照一行，要么落成自查清单一项或脚本检查项。

### 12.4 沉淀后必做

1. **规则与自查两处同步**：改了正文条款，必须同步第九节自查清单，否则下次交付仍会漏。
2. **能机检的落成脚本检查项**：硬规则加进 `scripts/check_original_need_md.py` 并跑一遍。
3. **回扫四处落点**：本文件正文、`references/structure-playbook.md`、`assets/template.md` 的表头与骨架、自查清单——改一处核其余三处（模板留着旧写法是最常见的存量漂移）。
4. 在 `references/feedback-log.md` 追加一行：`日期 / 原话节选 / 类别 / 归属 skill / 落点 / 处置`。
5. 跑一次脚本确认没改坏；用一句话告知用户「这条我记进 cyx-original-need-md 了，以后默认这样做」，方便他当场纠正。

### 12.5 规则也会过时：允许回退

用户推翻某条 → ① 改对应条目并**标注适用边界**，不直接删除；② 在 feedback-log 追加「规则回退」；③ 查有无其他条目与之冲突（尤其「三、阶段切法」与「五、缺口池」之间、「一、骨架」与自查清单之间）。

# 逐段写法详解（structure-playbook）

本文件是 `SKILL.md`「一、产出物骨架」的展开。**每写一段前翻对应小节**：这里只写「这段必须回答什么问题、容易写错在哪、判据是什么」。

文中范例取自一份真实跑通的稿子（LumenFlow 短剧 AI 平台，五阶段），用 `例：` 标出。范例只作写法参考，阶段数、入口名、用户角色都要按手上的产品换。

---

## 一、导语三块（正文之前，各占一段）

正文之前不分小节，用三段引述块把全篇的前提交代完。三块缺哪块，读者都会在读表的时候卡住。

| 块 | 必须回答 | 常见错误 |
|---|---|---|
| ① 能力底座与演进路径 | 这个产品靠什么能力（模型 / 数据 / 供应链）；上层应用走了哪几轮，每轮一句话 | 写成公司介绍、融资经历、团队规模；把「哪几轮」写成流水账而无「每轮一句话」的概括 |
| ② 始终在解的核心矛盾 | 贯穿全篇的那一对（或几对）张力；商业上要同时照顾的几类人 | 写成价值观口号（「以用户为中心」）；只写矛盾不写「几类人」——后者是后面「目标用户」列和主线的伏笔 |
| ③ 编号口径声明 | 阶段编号是功能逻辑顺序，不严格等于上线先后；**有偏差时逐条说明偏差** | 不写这一块，导致后面「为什么阶段 1 的入口反而最晚补上」被当成错误；或者写了偏差却不给理由 |

**判据（第②块）**：把这段念给一个不懂这行的人，他能不能说出「哦，所以这个产品一直在纠结 A 和 B 之间怎么选」？说不出 → 重写。

**偏差声明的写法**：先说结论（编号是逻辑顺序），再给一条观察证据，最后一句交代两类顺序各自的意义。例：

> 关于阶段编号与实际上线顺序的说明：下表中的阶段 1–5 是**功能逻辑演进顺序**（从单镜头 → 工程化），不严格等于各入口的实际上线先后。据当前产品界面观察：左侧「创作」工作台（阶段 1 单镜头能力的当前形态）是在【出海转绘】（阶段 3）之后补齐到左侧导航的；【新画布】（阶段 5）则为最后规划、近期上线的入口。

## 二、演进阶段总览（8 列）

一行一阶段。这张表是全文的目录，也是链式闭环的账本。

| 列 | 写什么 | 判据 / 常见错误 |
|---|---|---|
| 阶段 | `阶段N：{一句话形态名}` | 形态名要和正文 `### 阶段N` 标题**逐字一致**，否则读者要猜是不是同一个阶段 |
| 产品形态 | 这一阶段产品长什么样，一句话 | 写「支持 XX 功能」是功能不是形态；形态回答「用户拿到手的是什么」 |
| 核心入口 | 入口名（有多个就都列） | 入口名要与产品界面上的实际文案一致 |
| 实际入口上线/现状 | 这个入口现在挂在哪、什么时候补上的 | 未上线的写「规划中」；这一列是口径声明③的落点，不能空 |
| 解决核心痛点 | 用户当时最难受的是什么 | 写用户视角的处境，不写「提升效率」这类判断 |
| 目标用户 | **角色名** | 反例：「创作者」「企业用户」。正例：「编剧、小白创作者」「AI 动画师、短剧制作人、抽卡师」——业务材料里披露的岗位（如公司短剧团队设 20 名专职抽卡师）要落进这一列 |
| 关键需求 | 需求侧要点，用 `→` 串成流程 | 不写功能清单、不写模型名与参数；这一列是流程梗概，细节留给正文 |
| 遗留问题，催生下一阶段 | 这一阶段的天花板，并**点名**催生哪个阶段 | 列名里带「催生下一阶段」，写的时候就必须点出阶段号；漏点号的，脚本组 4 会报 |

**表里短、详情长**：总览表每格控制在两行内；机制、参数、上限、按钮文案全部下放到正文阶段小节。表里塞满一格里三百字的段落，这张表就废了。

## 三、分阶段拆解（八要素）

### 3.1 阶段标题

`### 阶段N：{形态名}（【{入口名}】）`。形态名与总览表逐字一致，入口名加 `【】` 便于眼跳。

### 3.2 八要素逐块写法

**（1）背景与原始需求**

上一阶段跑通后，**谁**提出了**什么**新要求。开头一句必须把上一阶段的遗留问题接住——这是链子上的扣。

- 写「谁在提」：已有用户扩张出的新角色（MCN、版权方、出海团队），还是新客群；
- 写「拿什么替代过」：这批人现在用什么凑合、代价是什么。没有替代方案的诉求往往不紧急，这一点能帮你判断该不该算一阶段；
- 句末标来源：`（白皮书口径）`、`（业务介绍披露）`。

例：

> 阶段2 的一键成片跑通后，大量已有国内成片的团队、MCN、版权方提出：手上已有实拍或动画短剧原片，能不能直接转成外语配音/字幕、替换画风，快速生成可海外分发的版本？

**（2）用户需求**

编号列表，**动词开头**，写人想干什么，不写功能名。

| 反例 | 正例 |
|---|---|
| 需要资产库 | **快速出海适配**：上传现成视频，自动识别剧本、角色、场景，完成多语言配音与字幕本地化 |
| 支持多语言 | **低门槛批量生产**：不需要重新写提示词、重新搭工作流，输入原片即可输出海外版 |

**判据**：这条需求里出现产品界面的功能名（资产库、分镜版、工作台）→ 说明你写的是功能不是需求，退回重写。

**（3）实现功能**

两句话：产品做出来的是什么（一句），机制是什么（一句）。不展开界面细节，那是下一块的事。

**（4）当前入口形态（据产品界面观察）**

这一块是全文最容易写空的地方，也是最能看出稿子有没有下过功夫的地方。要写：

- 入口位置（左侧导航 / 首页 Tab / 我的项目卡片）；
- 点进去之后的操作顺序（用 `→` 串，或分行列）；
- 参数有哪些档位（比例、时长、分辨率、模型、语言）；
- 按钮文案与提示文案（**照抄界面原文**，别改写成你自己的说法）；
- 上限与不可逆约束（如「创建后不可修改」「最多 9 张图片、3 个视频，合计不超过 9 个」）；
- 状态与反馈（待生成、已保存、消耗预估）。

**标来源**：「（据产品界面观察）」。界面观察只主张「现在怎么做」，不能升级成「官方承诺这么做」。没有界面材料时，这一块写「待补观察」，不要凭材料想象界面。

**（5）满足与痛点**

两块分开写，用加粗文字标签起行：

```markdown
- **满足需求**：{解决了什么}。
- **暴露痛点**：{逐条编号，每条带证据}。
```

**不用图标**。`✅ 满足需求` / `⚠️ 暴露痛点` 是 md 里的图标用法，渲染器之间不一致，改成正例那两行。

**（6）该阶段的产品局限（驱动下一阶段迭代）**

一句话说清天花板，并**点名**催生哪个阶段。写法：{天花板是什么，为什么它在这一阶段的框架内过不去} → 催生阶段N+1 的 {形态名}。

**判据**：写完这段，把它和下一阶段的「背景与原始需求」并排读。读起来像「上一句说缺什么，下一句说于是要做什么」→ 过；像两件不相干的事 → 回去改，或者承认这两阶段是并列关系。

**（7）用户反馈**

引述一段用户原话，用引述块。是用户的口吻，不是分析者的判断。

例：

> 用户反馈：一键成片看着美好，但精品生产完全不可用，我希望"大部分自动化，出错的地方我可以改到更细，不用只能整条分镜重跑"。

没有真实用户原话时：不编。要么去掉这一块（该阶段材料里确实没有），要么把它改成材料里的官方口径并换标签（如「业务侧视角」）。

**（8）业务侧视角**

这个入口在商业上承担什么。指向**具体客户类型**或**产能 / 成本指标**。

| 反例 | 正例 |
|---|---|
| 提升产品竞争力 | 这个入口承接内容出海流量，把国内已有的成熟内容资产复用到海外市场，拓展 B 端与 MCN 客户 |
| 增加用户粘性 | 这个入口承担产品冷启动引流，新用户进来零成本上手，立刻看到模型效果，降低用户流失 |

### 3.3 阶段之间的同构要求

各阶段的块名、块顺序、标签用法必须完全一致。**同构是这套稿子可比较的前提**——读者读到阶段 4 时会自动拿它和阶段 3 对齐，块名不一致他就得重新找。

某阶段材料确实缺某一块时：显式写「本阶段材料未覆盖」并说明，不要静默删掉那一块——静默删掉，读者会以为是漏写。

## 四、{N} 层入口架构（4 列）

演进讲完，把**当前**的产品入口按落位重排一遍。这一步的价值在于：演进顺序和「用户该点哪个」的顺序不是一回事，读者真正需要的是后者。

| 列 | 写什么 |
|---|---|
| 层级 | 从最轻到最重命名，用「能力档」的说法（快速测试 / 快速粗片 / 出海分发 / 自主创作 / 精细制作） |
| 能力 | `【{入口}】{一句话能力}` |
| 当前入口位置 | 左侧导航 / 首页 Tab / 我的项目卡片 |
| 备注 | 上线时机，或与相邻入口的关系（如「与出海转绘并列于首页」） |

表后必须点出**最大遗留体验问题**，用引述块写一句。例：

> 此时产品最大遗留的体验问题：**5 个入口能力差异大，普通用户难以快速判断"该点哪个入口"，认知门槛高**。

这一句不是客套——它通常就是缺口池里第一条的来源。

---

## 五、产品演进背后的 N 条核心需求主线

主线是**贯穿两个以上阶段的拉扯**，不是阶段特征的复述。

**判据**：这条主线能不能解释两个以上阶段的取舍？只能解释一个阶段的，那是阶段特征，不是主线。

每条主线的内部三段推进：

1. **两端各自的做法**——自动模式怎么做，手动模式怎么做；或早期怎么做，现在怎么做；
2. **各自的代价**——上手简单但算力浪费 / 可控但劳动密集；用完即丢但省事 / 可复用但要维护；
3. **落到哪些功能上 + 一句行业判断**——如「精细改，不必推倒重来」「AI 短剧工业化的核心不是生成一两个镜头，而是稳定复用一套角色世界观，持续产出多集内容」。

**覆盖面自检**：几条主线最好分别落在「交互」「技术资产」「商业」三个面上。三面都覆盖，读者才会觉得这份演进稿把产品看完了；三条都在讲交互，说明另外两个面没提炼出来。

## 六、现存需求缺口（后续迭代需求池）

| 列 | 写什么 | 判据 |
|---|---|---|
| 编号 | `G-n`，连续 | 带连字符，与模块式编号 `G1` 区分（同文档并存时不混用） |
| 缺口 | 还差什么能力，一句 | 写能力，不写「优化体验」 |
| 现状证据 | 哪份材料 / 哪个界面现象说明它还没解 | **必须能指回去**；指不回去的，是判断不是缺口 |
| 影响 | 不做的后果，或它值多少 | 落到具体的人或成本，不写「影响体验」 |

**与「阶段局限」严格区分**——这是本 skill 最容易混的一处：

| | 阶段局限 | 需求缺口 |
|---|---|---|
| 时间轴 | 历史，已被下一阶段解决 | 现在，还没解 |
| 位置 | 阶段小节内的「产品局限」块 | 独立章节的缺口池 |
| 作用 | 解释下一阶段为什么存在 | 变成下一版的需求池 |

落笔前过一遍：这条是不是已经被某个后续阶段解决了？是 → 它属于阶段局限，不进缺口池。

缺口的**来源通常有三处**，找不齐时按这三处扫一遍：① 入口架构表后的「最大遗留体验问题」；② 各阶段「暴露痛点」里至今仍在的；③ 业务材料里写了、界面里没有的（承诺与实现的差额）。

## 七、用户旅程视角的需求流转

用代码块把阶段串成一条链，一阶段一行，每行格式：

```
{动作}（需求：{一句}）
→ {动作}（需求：{一句}）
```

这一块是**给读者做验收用的**：他顺着这条链走一遍，如果中间有一步「为什么从这里跳到那里」说不通，说明前文的链子有断点。它同时也是下游 PRD 用户故事的直接素材。

注意区分它与前三张表的分工：总览表按阶段横排，入口架构按当前落位横排，用户旅程按**时间顺序纵向**走一遍——三个视角都写了，读者才既看得到结构、又看得到路径。

---

## 八、可进一步产出方向（可选）

一节三到五条，指向下游动作（PRD 用户故事、竞品对比、埋点指标）。**只列方向，不在这里做**——写在这里就做完了，等于把下游 skill 的活干了，两份产物还会互相打架。实际产出按 `SKILL.md` 第十一节转出去。

## 九、返工最多的五个原因（交付前逐条自查）

1. **阶段切错**：把「同一个入口加了个按钮」当新阶段，或把两件事塞进一个阶段。回第三节三条判据重切。
2. **链子断**：某阶段的遗留问题，下一阶段没接住；或下一阶段的背景凭空出现。把总览表最后一列和每阶段第一段并排读一遍，能抓出来。
3. **总览表被塞满**：表格格子写成小作文，机制与参数该下放的下放。
4. **无来源的产品事实**：价格、上限、客户名没标来源。逐条挂标签，挂不上的降为待确认。
5. **阶段之间不同构**：有的阶段有「用户反馈」块、有的没有，块名写法也不一样。统一块名与顺序，缺材料的显式写明「本阶段材料未覆盖」。

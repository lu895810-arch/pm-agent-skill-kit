# 需求优先级判定（cyx-priority-need）

## Purpose（目的）

把「一批需求 + 一个版本目标」变成一份**能直接拿去评审会讨论的优先级判定报告**。

这份报告的产出是一份**结构化的优先级评估**：每条需求给出 P0/P1/P2/P3 判定、一句话结论、判定依据、RICE 辅助打分、风险提示与行动建议，最后汇总本版本的分级清单并提示 P0 数量是否超标。它来自一份真实跑通的需求评审方法（Product-Priority-Ranker），那份方法做对的三件事，也是本 skill 的交付标准：

1. **规则先于分数**——先按 P0~P3 的定性规则判定，RICE 分数只作辅助参考；合规类需求直接判 P0，不被分数绑架。
2. **结论可反驳**——每条判定都给依据（用户价值/业务价值/依赖/风险），评审会上能当场讨论、能推翻。
3. **依赖与风险显式可见**——强依赖关系会反向拉高被依赖项的优先级，风险（合规/第三方API/技术）单列提示，不藏在一句话结论里。

**与既有 cyx 技能的分工（不重复造）**：

| 事项 | 归谁 |
|---|---|
| 单文件暗色科技风 HTML 模板、组件类、P0-P3 徽章自动着色、进度条/导航/返回顶部 | **本 skill** |
| 优先级判定的「规则 + RICE + 约束 + 输出模板」 | **本 skill** |
| 语言纪律（去 AI 味、通俗、逻辑闭环、衔接流畅、跨格式语言总纲） | `cyx-md-style` + `~/.workbuddy/MEMORY.md`「语言总纲」 |
| 视觉纪律（暗色科技风配色、反塑料味、去 emoji） | `cyx-html-style` |
| 整盘产品规划（架构/模块/优先级矩阵/MVP/路线图） | `cyx-strcuture-need` |
| 轻量需求 brief（每条带验收要点） | `cyx-summary-need` |
| 十章工程级 PRD（EARS 六段式） | `cyx-ears-need` |
| 素材分区、成品归档、文件命名 | `cyx-doc-separate` |

## When to use（何时触发）

**触发**：

- 用户有一批需求，要给它们**排优先级 / 分级**（P0/P1/P2/P3），用于需求评审、版本规划、需求池排序。
- 用户说「帮我把这批需求排个优先级」「做个需求评审稿」「这批需求哪些必须进 V1」「用 RICE 打一下分」。
- 用户手里有需求清单（名称/描述/覆盖用户/业务影响/工作量/依赖/风险），要一份能直接看、能讲、能评审的分级报告。
- 用户要的是「判定 + 依据 + 风险」的排序结论，不要求整盘产品规划或工程级 PRD。

**不触发**：

- 用户要的是整盘产品规划（架构/模块/矩阵/MVP/路线图）→ `cyx-strcuture-need`。
- 用户要的是需求条目文档（带验收要点）→ `cyx-summary-need`；重型十章 PRD → `cyx-ears-need`。
- 用户要做市场调研、不涉需求分级 → `cyx-research-report`。
- 纯技术方案设计、排期估算 → 不在本 skill 范围。

## 零、输入约定（先读这段再动手）

本 skill 的输入是一组结构化字段。缺字段就问，不要猜：

| 字段 | 说明 | 是否必填 |
|---|---|---|
| `product_name` | 产品名称（例：AI情感陪伴虚拟人） | 必填 |
| `target_version` | 目标版本（例：V1首发版本） | 必填 |
| `business_goal` | 当前版本的**业务目标**（例：完成 MVP 验证、拿到首批种子用户） | 必填 |
| `requirement_list` | 需求数组，每条含以下子字段 | 必填 |
| └ `req_name` | 需求名称 | 必填 |
| └ `req_desc` | 需求详细描述 | 必填 |
| └ `user_scope` | 覆盖用户范围：全部用户 / 大部分 / 部分 / 极少数 | 必填 |
| └ `business_impact` | 业务影响：留存 / 转化 / 付费 / 合规 / 无 | 必填 |
| └ `estimate_effort` | 预估工作量（人天） | 必填（用于 RICE 分母） |
| └ `dependency` | 依赖哪些功能/模块（无则写「无」） | 必填 |
| └ `risk` | 风险说明（合规、技术、外部API） | 必填 |

**判据**：缺 `business_goal` 就无法判定 P0/P1（P0 看「缺失是否阻断核心任务」、P1 看「是否主打价值」），所以业务目标必须明确。缺其他字段，先按常识给一版假设并显式标「假设待确认」，不要卡住。

**优先级是版本维度**：同一需求在不同版本可能不同级。本 skill 的输出只针对 `target_version` 这一个版本，不要当成永久标签。

## 一、优先级定义（判定标准，严格照此执行）

### P0【阻断上线｜版本底线】

满足任意一条即判 P0：

1. 属于产品**核心主流程必经环节**——缺了它，用户无法完成产品最核心的任务。
2. **合规 / 安全 / 监管强制要求**——不做会导致产品无法上线、下架、巨额处罚。
3. **核心阻塞性缺陷**——核心流程崩溃。

约束：单个版本 P0 数量**尽量 ≤5 项**；P0 必须全部完成，版本才能发布。

### P1【核心价值｜版本主打卖点】

不属于 P0，满足任意一条：

1. 是产品**主打价值**，用户使用本产品的核心诉求。
2. 覆盖**大量目标用户**，直接影响留存、转化、付费。
3. **竞品标配能力**——缺失会导致产品没有基础竞争力。

约束：P1 是本版本重点交付，资源充足必须做完；资源极度紧张可评估裁剪，**裁剪会削弱产品竞争力**（必须显式说明削弱什么）。

### P2【体验增强｜锦上添花】

非 P0/P1，满足任意一条：

1. 优化体验细节、提升好感，但**不阻断核心业务流程**。
2. **部分用户**高频需求，不是全部用户刚需。
3. 竞品有，但不属于核心标配，属于加分特性。

约束：P2 在 P0、P1 全部完成后，剩余资源再安排；资源不足直接延后到下个版本。

### P3【远期优化｜低价值创意】

不属于 P0/P1/P2，满足任意一条：

1. **小众低频需求、创意想法、远期规划**。
2. 体验微调，投入产出比较差。
3. 用户可通过其他方式绕开该问题，替代性强。

约束：本版本不安排开发，放入需求池，后续版本再评估；大部分 P3 最终直接砍掉。

### 判定顺序（硬性）

1. 先过 P0 三条——命中任一条即 P0，不再看 P1/P2/P3。
2. 未命中 P0 再过 P1 三条——命中任一条即 P1。
3. 未命中 P1 再过 P2 三条——命中即 P2。
4. 三条都不命中 → P3。

## 二、RICE 打分规则（辅助量化，0~100 分）

公式：`RICE = (Reach × Impact × Confidence) / Effort`

| 维度 | 取值 | 含义 |
|---|---|---|
| **Reach（覆盖用户）** | 1~5 | 5=全部目标用户；4=大部分；3=部分；2=少数；1=极个别 |
| **Impact（业务/用户影响）** | 1~5 | 5=极大（直接影响留存/上线）；4=高；3=中等；2=低；1=几乎无影响 |
| **Confidence（确定性）** | 0.2~1 | 1=需求清晰、有用户证据；0.5=推测、缺验证；0.2=猜测、需求不确定 |
| **Effort（开发工作量）** | 1~10 | 越大代表投入成本越高，分母越大，最终分数越低 |

**使用纪律**：

- 分数**仅作辅助参考**，**规则优先级高于单纯分数**——合规类需求直接判 P0，不受分数限制。
- Reach 取值对应 `user_scope`：全部用户=5、大部分=4、部分=3、极少数=1；Confidence 默认 0.5（推测），有用户证据取 1，纯猜测取 0.2。
- 输出时必须同时给「定性判定（P0~P3）」与「RICE 分数」，二者并列，方便评审对照。

---

## 三、判定约束（硬性，不可违背）

1. ❌ **不能以开发难度高低直接判定优先级**：难做 ≠ P0，简单 ≠ P0。
2. ❌ 不能只依据「业务方 / 老板想要」直接标 P0——必须转化为用户价值、业务价值或合规风险，写进依据。
3. ❌ 优先级是**版本维度**，不是永久标签；同一需求不同版本可变化。
4. ✅ 存在强依赖：A 依赖 B，则**B 的优先级必须 ≥ A**（被依赖项不能比依赖方低）。
5. ✅ 输出必须区分：定性判定 + 定量 RICE 分数，并给出**可反驳理由**，方便评审会讨论。

---

## 四、执行流程（Agent 执行步骤）

1. 读取输入：产品名称、版本、业务目标、需求清单。
2. 逐条解析：用户范围、业务影响、依赖、风险。
3. 第一步：定性判定，对照 P0/P1/P2/P3 规则（按 第一节 的判定顺序）。
4. 第二步：计算 RICE 辅助打分。
5. 第三步：检查依赖关系，修正优先级（被依赖项 ≥ 依赖方）。
6. 第四步：识别风险（合规、第三方 API、技术债务），单列提示。
7. 输出结构化结果：优先级、一句话结论、判定依据、RICE 得分、风险、行动建议。
8. 汇总：本版本 P0~P3 清单 + P0 数量是否超标提示。

## 七、技能边界（不能做什么，写进文档）

1. 本 skill 只做**优先级判定**，不做需求挖掘、用户调研、技术方案设计。
2. 无法自动判断需求真实用户痛点，**依赖输入信息准确性**；输入信息错误，分级结果就会错。
3. 不会替代产品评审会议，输出结果是**评审参考**，不是最终决策。
4. 无法自动评估跨团队外部资源排期，外部依赖需人工补充校验。

## 九、自我进化机制（遵循 cyx-skill-evolution 通用条款）

> **上游通用条款**：判定、留痕、回退的共性规则见 `cyx-skill-evolution`；本节是它在需求优先级判定场景的落地。

**技能不是一次写死的。** 用户就优先级判定提的每一条修改意见，都可能适用于所有后续同类判定；通用项写回本文件，本 skill 才会越用越准。

### 9.1 触发时机

- 用户对**判定规则 / 分级口径 / RICE 取值 / 输出格式**提意见。
- **同一类意见反复出现（≥2 次）**——最强信号：不是当期报告的问题，而是默认写法错了，要升为强约束。
- **每完成一次交付就过一遍**（哪怕用户一句意见都没提）——按 9.4 回扫本轮交互。

### 9.2 落点映射

| 代号 | 反馈类型 | 典型原话 | 落点 |
|---|---|---|---|
| D 结构与层次 | 判定顺序、P0~P3 定义边界 | 「这条不该判 P0」「P1 和 P2 的边界不清」 | 第一节 + 第八节自查 |
| B 遣词与命名 / E 术语 | 输出语言、依据写法 | 「依据写得太虚」「看不懂」 | 第五节输出模板 + 全局语言纪律 |
| A 事实与依据 | 输入口径、假设标注 | 「业务目标必须问」「不知道的标待确认」 | 零节输入约定 + 第八节 |
| F 排版与视觉 | HTML 模板着色、版式 | 「徽章颜色不对」「太像 AI 生成的」 | `assets/template.html` 的 CSS/JS + 全局视觉纪律 |
| G 流程与命令 | 工具执行 | 「这个命令跑不通」 | 第四节流程 |

### 9.3 落盘纪律（三不写）

1. **不与已有规则重复**：同类已在 → 就地强化，不新起一节。
2. **不写死具体数值**：写「判据 + 判定方法」，不写具体数字（数字会再变）。
3. **写不成判据的模糊直觉不进文件**：要么落成模板 CSS/JS 改动，要么落成自查清单一项。

### 9.4 每轮交付的自动回扫（不等用户开口）

1. **回扫本轮交互**：把用户从提需求到定稿说的话逐条过一遍，**尤其中途改口、推翻、补充的地方**。
2. **逐条判通用性**：只对当前这份报告成立（个案，只改当期产物），还是换一批需求、换一个版本仍成立（通用，回写本技能）？
3. **归类**：按 9.2 表取一个主类代号。
4. **定落点并回扫**：`SKILL.md` 正文 ↔ `assets/template.html` 的示例与着色 ↔ 第八节自查清单，改一处核其余。
5. **落盘 + 告知**：在 `references/feedback-log.md` 追加一行；一句话告知用户「这条我记进 cyx-priority-need 了，以后默认这么做。」
6. **没有可沉淀的就明说**：告诉用户「本轮没有需要写回技能的规则」。
